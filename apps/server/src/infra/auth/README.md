# Authentication

Call `authConfig(environment, smtpConfigured)` at startup. It requires an `AUTH_SECRET` of at least 32 characters, implements `AUTH_PASSWORD_LOGIN=auto|on|off`, and rejects password login or missing install SMTP in `TENANCY=multi`. Email is decided per gym: a gym uses its own SMTP settings when saved (`areas/settings/smtp.ts`), otherwise the install's `SMTP_*`. Under `auto`, `passwordLogin(config, smtpConfigured)` turns password login on only for a gym with neither.

After database initialization, create `createAuthService({ config, sendMagicLink })` and mount `sessionMiddleware({ auth, resolve, smtpConfigured })` after tenant resolution. For login endpoints the middleware passes the gym's email availability to `bind` (`smtpConfigured`), which enables magic links and, under `auto`, disables password login for that gym; without it, the install-level settings apply. `resolve` must return the resolved gym ID, its canonical origin from trusted tenant configuration, and the socket IP or an address validated by the trusted proxy. Incoming forwarded headers are stripped. Do not pass an unvalidated request host as the canonical origin. Mount `authorize` from `areas/staff/auth.permissions.ts` with the route registry. The middleware sets staff roles from the current gym; a member surface can inject its own principal loader, which receives the verified session (its ID and the portal household it has chosen). `requestSession(request)` returns that session to routes that store a session preference; it is attached by the middleware only and is never read from request input.

The HTTP wrapper exposes only password sign-in when enabled, magic-link request/verification when delivery is configured, Google sign-in and its callback when the Google extension is configured, get-session, and sign-out. Every other library endpoint returns 404. Responses do not contain session bearer tokens. Magic tokens contain the issuing gym ID, are stored hashed, expire after five minutes, and are consumed once. Callback origins and destinations are reconstructed from the gym configuration: a verified magic link lands on `/admin`, except a portal claim callback (`/portal/claim?claim=<code>` on the gym's own origin, with a code of the expected shape), which is rebuilt from its validated code. `sendLoginLink(email, claimCode?)` sends such a link.

Google sign-in (`google.ts`) is on when the instance's configuration has an OAuth client: `googleFromEnvironment(env)` reads `GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET` (both or neither; empty is unset; `null` in demo mode), the only source in either tenancy mode. Pass `createGoogleAuthExtension({ credentials })` as the service's `google` option; only then do `POST /sign-in/social` and `GET /callback/google` exist. The extension's per-gym plugin writes the issuing gym into the OAuth state's server context (`addOAuthServerContext`), and its `beforeRequest` accepts the sign-in only with the body `{ "provider": "google" }` and the callback only with one state whose stored row (`auth-state:<state>` in `auth_verification`, kept in the database) is unexpired and names the resolved gym; anything else is a 403 before Better Auth exchanges the code. The service turns off sign-up and ID-token sign-in for the provider and trusts no provider for linking, so a Google account joins an existing identity only when both its address and the identity's are verified (`requireLocalEmailVerified`); otherwise the callback returns to `/login?error=account_not_linked`, and an unknown address to `/login?error=signup_disabled`. A successful callback lands on `/admin`, which sends members on to the portal. An account hook nulls provider tokens, so `auth_account` keeps the Google account ID and no tokens, and a restore has none to re-encrypt.

`sendMagicLink` receives `{ email, url, gymId }`; `createAuthEmailSender(smtpFor)` renders `renderAuthLink` with the locale translator and sends it through the issuing gym's SMTP settings. The install fallback reads `SMTP_HOST`, `SMTP_PORT` (default 587), `SMTP_FROM`, optional `SMTP_USER`/`SMTP_PASS`, and `SMTP_SECURITY=starttls|tls|plain` (default `starttls`). Always use a sending service (Postmark, Brevo, Amazon SES, or similar); mail sent directly from a server usually lands in spam. Delivery runs outside database transactions. Public signup is disabled; account methods provision lowercase identities and accept an optional transaction callback for gym access. Without that callback they grant no role or household link.

`createOwnerService` in `areas/staff/auth.owner.ts` is the shared gym-creation/setup service. It provisions the identity, owner role, and audits in one transaction, then sends the login link through the bound auth service. Setup without email supplies a password instead; retries verify the existing credential and never replace it. Duplicate identities and grants are suppressed by database constraints; an existing different staff role is rejected. Retrying after an email failure may resend a login link. No bearer link appears in CLI output.

`GET /api/auth/bootstrap` uses the shared shell contract and is owned by `areas/staff/auth.bootstrap.ts`. Session middleware resolves the login before passing this path to the route registry. The response contains only the resolved gym's public shell fields, current user's roles/member access and display name, and password/magic-link modes for this gym (`configureLoginMethods`); it is never cached. The roles are the ones the session middleware already resolved for the request. The display name is the staff profile in this gym, else the member the login is linked to (the open household's, for a portal login; an erased member names no one), else the login's own name, and those records are read through `forGym` in one `household_users` query, so they are never another gym's. The login's own name (`auth_user.name`) is install-wide, so only `TENANCY=single` uses it, falling back to the login's email when it is blank; in `multi` mode it may be the name typed at whichever gym first provisioned the address, so the login's email stands in for it. The bound session decides this from the service's own config (`BoundSession.userName`), so the bootstrap needs no mode of its own. A request with no session has no login to name, and the name is `null`: the shell shows its generic "Signed in" label, never the user ID. Normal auth records retain Drizzle's UUIDv7 defaults; Better Auth's UUID ID strategy makes deterministic verification reservations compatible with PostgreSQL as well.

Password hashes use Node's asynchronous Argon2id, NFKC normalization, a random 16-byte salt and a 32-byte tag, encoded as `$argon2id$v=19$m=19456,t=2,p=1$<salt>$<hash>`. Verification accepts precisely this bounded format. A process shares two native hash slots (about 38 MiB of Argon2 working memory) and at most 64 pending requests; excess work is rejected. The burst test reports local latency and RSS. Whole-server memory measurements require the deployment environment.

`resetStaffPassword` rechecks the current actor and target staff roles and household links, updates the credential, deletes all target sessions and writes the audit in one transaction. The auth system pool also enters `forGym` for this operation, so business-table RLS still restricts roles and household links to the chosen gym. Passwords and hashes are absent from audit data. `assertCanResetPassword` is reusable by other reset flows.

Before dispatching CLI commands, initialize the database and call `configureAuthCli({ resolveGymId, smtpConfigured })` with the single-gym resolver; `core/runtime.ts` does this for `gym-app`. `gym-app auth reset-password <email>` prompts for a hidden password twice, requires a current owner, revokes every session and audits as the system. No password is accepted in command arguments or environment variables.

Portal sessions store their chosen household in `auth_session.household_id` through `createPortalSessionStore` (`portal-sessions.ts`), which checks the user's household link in the same transaction and audits the choice. It is a preference, not a grant: the portal principal loader checks it against the user's current household links on every request. Portal invitations (`portal-invitations.ts`) store hashed, gym-bound tokens for a household login that is created only on acceptance. Their `auth_verification` rows also carry `gym_id`, `household_id`, `user_id` and `scope` (the binding's `payer` or `member`), which only this module sets (Better Auth's own rows, whose values aren't JSON, leave them null); partial indexes serve the lookups, and the identifier's gym prefix is still checked. Migrations 0013 and 0014 backfill them for invitations a process on an earlier release wrote. `outstanding` lists one household's unexpired invitations for staff (gym-scoped, never the token), `withPayerInvitations` runs a read in one gym transaction on this pool with a condition for households with an unexpired payer invitation (the dashboard's confirmation shortlist leaves them out in the same query), and `revoke` deletes one in a transaction that also runs the caller's audit. `expire` deletes a gym's expired invitations and claim holds in batches; `createPortalInvitationExpiryJobs` (`areas/members/household-users.invitations.ts`) runs it hourly for each gym. `sweepExpired` deletes the install's other expired verification rows (magic links, staff invitations), once an hour for the whole install: `registerVerificationSweep` registers it as a system job, which the runtime schedules. Better Auth's own cleanup is off (`service.ts`): it deleted every expired row on each sign-in, so expired invitations went before their invitees could be removed. Better Auth still refuses an expired token itself. Revoking and expiry also delete the invitee identity an invitation provisioned when it has no account and no other invitation row or claim hold. Identities with an account or a link in this gym are filtered out first and never locked; the rest are locked in ID order and checked again in the delete: links, staff roles and history in any gym keep an identity through their foreign keys, which bypass row-level security, so the lock and the delete run in a savepoint, a refused batch releases its locks, and it is halved until each held identity stands alone. `removeGymInvitees` runs the same cleanup in the system transaction that deletes a gym (`areas/settings/gym-delete.ts`), before the gym's cascade would take its invitation rows. `createPortalClaimCodes(AUTH_SECRET)` signs the stateless, one-hour claim codes carried by passwordless claim callbacks; completion requires the signed-in session of the user the code names. A passwordless onboarding claim also writes a hold (`holdClaim`: a `portal-claim:<gym>:<link>` row with the same columns) that lasts as long as its code, so the cleanup keeps the identity while the claim is pending, even if an invitation for the same address is revoked or expires meanwhile; asking again replaces it, completion (`completeOnboarding`) deletes it, and `expire` sweeps an abandoned one with the identity it kept. Completion locks the user after the onboarding link and the hold, so a user that is gone anyway answers 404 (restart from the onboarding link).
