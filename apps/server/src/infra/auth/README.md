# Authentication

Call `authConfig(environment, smtpConfigured)` at startup. It requires an `AUTH_SECRET` of at least 32 characters, implements `AUTH_PASSWORD_LOGIN=auto|on|off`, and rejects password login or missing install SMTP in `TENANCY=multi`. Email is decided per gym: a gym uses its own SMTP settings when saved (`areas/settings/smtp.ts`), otherwise the install's `SMTP_*`. Under `auto`, `passwordLogin(config, smtpConfigured)` turns password login on only for a gym with neither.

After database initialization, create `createAuthService({ config, sendMagicLink })` and mount `sessionMiddleware({ auth, resolve, smtpConfigured })` after tenant resolution. For login endpoints the middleware passes the gym's email availability to `bind` (`smtpConfigured`), which enables magic links and, under `auto`, disables password login for that gym; without it, the install-level settings apply. `resolve` must return the resolved gym ID, its canonical origin from trusted tenant configuration, and the socket IP or an address validated by the trusted proxy. Incoming forwarded headers are stripped. Do not pass an unvalidated request host as the canonical origin. Mount `authorize` from `areas/staff/auth.permissions.ts` with the route registry. The middleware sets staff roles from the current gym; a member surface can inject its own principal loader.

The HTTP wrapper exposes only password sign-in when enabled, magic-link request/verification when delivery is configured, get-session, and sign-out. Every other library endpoint returns 404. Responses do not contain session bearer tokens. Magic tokens contain the issuing gym ID, are stored hashed, expire after five minutes, and are consumed once. Callback origins and destinations are reconstructed from the gym configuration. The Google extension requires an explicit state-binding callback before it exposes its two provider routes.

`sendMagicLink` receives `{ email, url, gymId }`; `createAuthEmailSender(smtpFor)` renders `renderAuthLink` with the locale translator and sends it through the issuing gym's SMTP settings. The install fallback reads `SMTP_HOST`, `SMTP_PORT` (default 587), `SMTP_FROM`, optional `SMTP_USER`/`SMTP_PASS`, and `SMTP_SECURITY=starttls|tls|plain` (default `starttls`). Always use a sending service (Postmark, Brevo, Amazon SES, or similar); mail sent directly from a server usually lands in spam. Delivery runs outside database transactions. Public signup is disabled; account methods provision lowercase identities and accept an optional transaction callback for gym access. Without that callback they grant no role or household link.

`createOwnerService` in `areas/staff/auth.owner.ts` is the shared gym-creation/setup service. It provisions the identity, owner role, and audits in one transaction, then sends the login link through the bound auth service. Setup without email supplies a password instead; retries verify the existing credential and never replace it. Duplicate identities and grants are suppressed by database constraints; an existing different staff role is rejected. Retrying after an email failure may resend a login link. No bearer link appears in CLI output.

`GET /api/auth/bootstrap` uses the shared shell contract and is owned by `areas/staff/auth.bootstrap.ts`. Session middleware resolves the login before passing this path to the route registry. The response contains only the resolved gym's public shell fields, current user's roles/member access, and password/magic-link modes for this gym (`configureLoginMethods`); it is never cached. Normal auth records retain Drizzle's UUIDv7 defaults; Better Auth's UUID ID strategy makes deterministic verification reservations compatible with PostgreSQL as well.

Password hashes use Node's asynchronous Argon2id, NFKC normalization, a random 16-byte salt and a 32-byte tag, encoded as `$argon2id$v=19$m=19456,t=2,p=1$<salt>$<hash>`. Verification accepts precisely this bounded format. A process shares two native hash slots (about 38 MiB of Argon2 working memory) and at most 64 pending requests; excess work is rejected. The burst test reports local latency and RSS. Whole-server memory measurements require the deployment environment.

`resetStaffPassword` rechecks the current actor and target staff roles and household links, updates the credential, deletes all target sessions and writes the audit in one transaction. The auth system pool also enters `forGym` for this operation, so business-table RLS still restricts roles and household links to the chosen gym. Passwords and hashes are absent from audit data. `assertCanResetPassword` is reusable by other reset flows.

Before dispatching CLI commands, initialize the database and call `configureAuthCli({ resolveGymId, smtpConfigured })` with the single-gym resolver; `core/runtime.ts` does this for `gym-app`. `gym-app auth reset-password <email>` prompts for a hidden password twice, requires a current owner, revokes every session and audits as the system. No password is accepted in command arguments or environment variables.
