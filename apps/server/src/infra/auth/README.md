# Authentication

Call `authConfig(environment, smtpConfigured)` at startup. It requires an `AUTH_SECRET` of at least 32 characters, implements `AUTH_PASSWORD_LOGIN=auto|on|off`, and rejects password login or missing install SMTP in `TENANCY=multi`. Email is decided per gym: a gym uses its own SMTP settings when saved (`areas/settings/smtp.ts`), otherwise the install's `SMTP_*`. Under `auto`, `passwordLogin(config, smtpConfigured)` turns password login on only for a gym with neither.

After database initialization, create `createAuthService({ config, sendMagicLink })` and mount `sessionMiddleware({ auth, resolve, smtpConfigured })` after tenant resolution. For login endpoints the middleware passes the gym's email availability to `bind` (`smtpConfigured`), which enables magic links and, under `auto`, disables password login for that gym; without it, the install-level settings apply. `resolve` must return the resolved gym ID, its canonical origin from trusted tenant configuration, and the socket IP or an address validated by the trusted proxy. Incoming forwarded headers are stripped. Do not pass an unvalidated request host as the canonical origin. Mount `authorize` from `areas/staff/auth.permissions.ts` with the route registry. The middleware sets staff roles from the current gym; a member surface can inject its own principal loader, which receives the verified session (its ID and the portal household it has chosen). `requestSession(request)` returns that session to routes that store a session preference; it is attached by the middleware only and is never read from request input.

The HTTP wrapper exposes only password sign-in when enabled, magic-link request/verification (and the switch that completes a link from the confirmation page below) when delivery is configured, Google sign-in and its callback when the Google extension is configured, get-session, and sign-out. Every other library endpoint returns 404. Responses do not contain session bearer tokens. Magic tokens contain the issuing gym ID, are stored hashed, expire after five minutes, and are consumed once. Callback origins and destinations are reconstructed from the gym configuration: a verified magic link lands on `/admin`, except a portal claim callback (`/portal/claim?claim=<code>` on the gym's own origin, with a code of the expected shape), which is rebuilt from its validated code. `sendLoginLink(email, claimCode?)` sends such a link.

A browser whose session belongs to another login doesn't switch on opening a link. `GET /magic-link/verify` with a session first reads the link's `auth_verification` row without consuming it (`linkLogin`: the token's hash, `linkTokenHash`, is the same SHA-256 base64url form Better Auth's `hashed` option stores, given as a custom hasher so `service.ts` can find the row). When the row is unexpired and names another login, it answers 200 with `loginSwitchPage`: server-rendered, no script, `no-store`, `Referrer-Policy: strict-origin` (its URL holds the token, so requests from it name only the origin; under `no-referrer` browsers send the form's POST with `Origin: null`, which the origin check refuses) and its own content security policy (no script, inline styles, forms to the gym's origin only, never framed), naming both addresses, with a form that posts the token (and a valid portal claim callback) to `POST /api/auth/magic-link/switch`, and a link back to `/`. That endpoint isn't in `authEndpoints`: `handler` takes it first, checks the session's gym and the request origin as for other POSTs, reads the form, refuses a token for another gym (403) or a body without one (400), and runs the same verify Better Auth would, with callbacks rebuilt from the gym. It signs in only as the token's own login, so the address limit on `/magic-link/verify` counts it too, and a token still signs in once, by whichever request uses it first. No session, the same login's session, or a row that is missing, expired or names no login forwards the verify as before.

Better Auth's cookies (session, sign-in state and the rest) are host-only (`crossSubDomainCookies` off), HttpOnly, SameSite=Lax and at `Path=/`. With `config.production`, which `bind` allows only with an `https:` origin, they are `Secure` and named `__Host-better-auth.<name>` (`advanced.cookiePrefix`, with `useSecureCookies` off so Better Auth adds no `__Secure-` of its own; `cookiePrefix(config)` gives the prefix), so no other host under the same parent domain can set one. Otherwise they keep the plain `better-auth.<name>`. In production a session is read only from `__Host-better-auth.session_token`, in either tenancy mode; a `__Secure-better-auth.*` or unprefixed cookie is ignored. The app's own cookies take the same prefix through `core/cookies.ts` (`configureCookies`, set by the runtime).

Sign-in has two limits (`signInLimits` in `account-limit.ts`), and a per-gym ceiling on login links described below, all in `auth_rate_limit`, so every app process shares them. Better Auth counts each client address per endpoint (password, magic-link request and verification, Google): 20 a minute, keyed by the trusted address `bind` was given. After that check admits a request, an `onRequest` plugin reserves the account's slot: 10 in a fixed ten-minute window, keyed by a keyed digest of the trimmed, lower-cased email under `AUTH_SECRET` whether or not an account has it (`accountDigest` in `account-limit-key.ts`, an HMAC from `createKeyedCommandDigest`; `authConfig` configures it once the secret passes its check, and any other use throws), so a row or a backup can't be tested against guessed addresses. The row never holds the address or a plain hash of it; open windows start again once when an install upgrades from the plain hash or changes `AUTH_SECRET`, and their old rows end and are pruned. The plugin is registered once on the Better Auth instance each `bind` builds, so these requests never build a second one; `handler` names each password or login-link call's account by a random ID in the internal `x-plaingym-account-attempt` header, which is stripped from incoming requests along with the forwarded-address headers, and each call keeps its own reservation. A password response of 200 releases its reservation; failed or interrupted attempts keep it. In-flight checks occupy slots, so concurrent guesses remain bounded. Login-link requests keep every reservation. A refusal never increments the account count or extends its window. Account rows hold the window's end so pruning never removes an open window; a reservation's row ID and window end prevent late successes from refunding a newer window. In `multi` mode both keys include the bound gym ID: `gymAddressStorage` supplies Better Auth's atomic rolling address counters using its normalized address/path keys. It prunes expired rows whenever an address window starts, including a new address's first one (Better Auth's own storage prunes only when an existing row's window restarts), and waits for the prune as Better Auth does here; a failed prune logs `auth.rate_limit_prune_failed` (the gym ID, the error's class and its database code) and still admits the request. It follows `createDatabaseStorageWrapper` in `better-auth/dist/api/rate-limiter` at the pinned `better-auth` version, so recheck the two on every Better Auth upgrade; `rate-limits.test.ts` fails when the pin changes, as a reminder. Single-gym keys and address-window behavior are unchanged. Either refusal is a 429 with `Retry-After` (and Better Auth's `X-Retry-After`) and the same body. `sendLoginLink` is internal and not limited.

A gym also sends at most 100 login links an hour (`loginLinkCeiling`, a fixed window under the key `ceiling|login-link|<gym>`, in both tenancy modes) to addresses with no staff role and no household login in that gym. Only the public `POST /sign-in/magic-link` request counts: the magic-link callback finds the call's attempt ID and checks the address in one gym transaction, and an address linked to the gym is never counted or dropped. The links the app sends itself through `sendLoginLink` (the first owner, portal claims, a join's sign-in link) are never counted. Every public request runs the linked check and then the same two ceiling statements (`reserveLoginLinkCeiling`: one upsert, then one read of the window's end), a linked address's never changing the count or creating a row that holds a send. A send that provably sent nothing (`deliveryAcceptance` is `not_accepted`) gives its ceiling slot back, only to the window it came from; one whose outcome is unknown keeps it. Past the ceiling nothing is sent (its `auth_verification` row is still written), and the request answers like a sent one. `createAuthService` keeps, per gym and shared by every binding, the durations of the gym's newest five real sends (every send counts, `sendLoginLink`'s too) and when the latest one failed through the sending service (`emailServiceFailure`); a success clears that time, a recipient refused at `RCPT TO` or a message refused at `DATA` (`emailRecipientRefusal`) clears it too without recording its duration (a refusal gives its ceiling slot back, so fast refusals must not shorten the dropped wait), and any other failure records nothing. A dropped request waits the median of those durations, at most `loginLinkAnswerWaitMs` (2 seconds), then answers 503 `EMAIL_UNAVAILABLE` when the latest send failed within `loginLinkFailureMemoryMs` (5 minutes), else 200; it logs no `auth.magic_link_email_unavailable` line. The record holds durations and times only, never an address or an error's text. What still differs: a process that has sent nothing for the gym since it started answers a dropped request at once with 200; a failure is imitated only for 5 minutes after it; a mail server slower than 2 seconds still answers later for a linked address; a failed send to an unlinked address gives its slot back with one more statement; the linked check runs one query for a staff address and two for any other; and each app process keeps its own record. Each process logs the first dropped send of a gym's window as `auth.login_link_ceiling`, with the gym ID and the limit, never the address. Tests may pass `rateLimit`, `accountRateLimit`, `loginLinkCeiling`, `now`, `pause` (the dropped request's wait) and `elapsed` (the monotonic reading that times sends) to `createAuthService`.

Google sign-in (`google.ts`) is on for a gym that has an OAuth client. `googleFromEnvironment(env)` reads the install's `GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET` (both or neither; empty is unset; `null` in demo mode), which win in either tenancy mode. It never throws: a malformed pair (only one set, whitespace, over 512 characters) counts as unset and is logged once per process as `auth.google_environment_invalid` with the variable and the reason, never the value, and `googleEnvironmentProblem(env)` reports the same for the Health tile and Settings. `checkGoogleClient(credentials, { redirectUri })` asks Google's token endpoint about a client before it is stored, outside any transaction and with a timeout: `invalid_grant` is `accepted`, `invalid_client` is `rejected`, anything else `unknown`. When the install sets no client, a single-gym owner may store the gym's own client, encrypted (`areas/settings/google-login.ts`, whose `createGoogleClientResolver` decides per gym and ignores the stored client in `multi` and demo mode). Pass `createGoogleAuthExtension({ credentials })` as the service's `google` option, with one client or a per-gym lookup `(gymId) => Promise<GoogleCredentials | null>`. The service asks it on each Google request, outside any transaction, and builds that request's Better Auth instance with the answer, so a client saved or removed while the server runs applies to the next sign-in; with no client for the gym, `POST /sign-in/social` and `GET /callback/google` answer 404, and without the option they never exist. The extension's per-gym plugin writes the issuing gym into the OAuth state's server context (`addOAuthServerContext`), and its `beforeRequest` accepts the sign-in only with the body `{ "provider": "google" }` and the callback only with one state whose stored row (`auth-state:<state>` in `auth_verification`, kept in the database) is unexpired and names the resolved gym; anything else is a 403 before Better Auth exchanges the code. The service turns off sign-up and ID-token sign-in for the provider and trusts no provider for linking, so a Google account joins an existing identity only when both its address and the identity's are verified (`requireLocalEmailVerified`); otherwise the callback returns to `/login?error=account_not_linked`, and an unknown address to `/login?error=signup_disabled`. A successful callback lands on `/admin`, which sends members on to the portal. An account hook nulls provider tokens, so `auth_account` keeps the Google account ID and no tokens, and a restore has none to re-encrypt.

When `sendMagicLink` fails through the gym's sending service (`emailServiceFailure` in `infra/email/failure.ts`: connection, TLS, a refused login or a refused sender address), `POST /api/auth/sign-in/magic-link` answers 503 with code `EMAIL_UNAVAILABLE` and logs `auth.magic_link_email_unavailable` with the gym and the failure class only; any other failure answers as before. Better Auth calls the sender for every address, so the answer is the same whether or not the address has an account, and a send the login-link ceiling drops (above) answers 503 the same way while the gym's latest real send failed. `sendLoginLink` rethrows the sender's own error. `sendMagicLink` receives `{ email, url, gymId }`; `createAuthEmailSender(smtpFor)` renders `renderAuthLink` with the locale translator and sends it through the issuing gym's SMTP settings, under a keyed send state named by a hash of the link: the same link sends once, and asking again creates a new link and sends it. The hourly email delivery upkeep deletes that send state once the five-minute link has expired and no attempt can still be in flight (`infra/email/README.md`). The install fallback reads `SMTP_HOST`, `SMTP_PORT` (default 587), `SMTP_FROM`, optional `SMTP_USER`/`SMTP_PASS`, and `SMTP_SECURITY=starttls|tls|plain` (default `starttls`). Always use a sending service (Postmark, Brevo, Amazon SES, or similar); mail sent directly from a server usually lands in spam. Delivery runs outside database transactions. Public signup is disabled; account methods provision lowercase identities and accept an optional transaction callback for gym access. Without that callback they grant no role or household link.

`createOwnerService` in `areas/staff/auth.owner.ts` is the shared gym-creation/setup service. It provisions the identity, owner role, and audits in one transaction, then sends the login link through the bound auth service. Setup without email supplies a password instead; retries verify the existing credential and never replace it. Duplicate identities and grants are suppressed by database constraints; an existing different staff role is rejected. Retrying after an email failure may resend a login link. No bearer link appears in CLI output.

`GET /api/auth/bootstrap` uses the shared shell contract and is owned by `areas/staff/auth.bootstrap.ts`. Session middleware resolves the login before passing this path to the route registry. The response contains only the resolved gym's public shell fields, current user's roles/member access and display name, and password/magic-link modes for this gym (`configureLoginMethods`); it is never cached. The roles are the ones the session middleware already resolved for the request. The display name is the staff profile in this gym, else the member the login is linked to (the open household's, for a portal login; an erased member names no one), else the login's own name, and those records are read through `forGym` in one `household_users` query, so they are never another gym's. The login's own name (`auth_user.name`) is install-wide, so only `TENANCY=single` uses it, falling back to the login's email when it is blank; in `multi` mode it may be the name typed at whichever gym first provisioned the address, so the login's email stands in for it. The bound session decides this from the service's own config (`BoundSession.userName`), so the bootstrap needs no mode of its own. A request with no session has no login to name, and the name is `null`: the shell shows its generic "Signed in" label, never the user ID. Normal auth records retain Drizzle's UUIDv7 defaults; Better Auth's UUID ID strategy makes deterministic verification reservations compatible with PostgreSQL as well.

Password hashes use Node's asynchronous Argon2id, NFKC normalization, a random 16-byte salt and a 32-byte tag, encoded as `$argon2id$v=19$m=19456,t=2,p=1$<salt>$<hash>`. Verification accepts precisely this bounded format. A process shares two native hash slots (about 38 MiB of Argon2 working memory) and at most 64 pending requests; excess work is rejected. The burst test reports local latency and RSS. Whole-server memory measurements require the deployment environment.

`resetStaffPassword` rechecks the current actor and target staff roles and household links, updates the credential, deletes all target sessions and writes the audit in one transaction. The auth system pool also enters `forGym` for this operation, so business-table RLS still restricts roles and household links to the chosen gym. Passwords and hashes are absent from audit data. `assertCanResetPassword` is reusable by other reset flows.

`changeOwnPassword` (the account service, for a login's own account page) is not a reset: it needs the login's current password, works only with password login on in `single` mode, and reserves a slot of the `/sign-in/email` account window before verifying, so wrong guesses spend the sign-in budget and a refused request never verifies; a right current password gets its slot back. The new hash is written in one transaction that locks the login, updates the credential only while it still holds the verified hash (otherwise `conflict`), deletes the login's other sessions in the gym (the asking session stays) and audits `auth.password_changed` without the password or hash. `createPasswordUser` (setup, password-mode portal onboarding claims) reserves the same slot before it checks a password against an address that already has a login, gives it back only once the caller's provisioning succeeds, and refuses a wrong password, a login with no password and (through `existingAccountRefusal`) a staff account with one `conflict`; `hasCredential` tells the staff invitation whether a login already has a password. `removeUnprovenPassword(tx, { gymId, userId, actorUserId, clock })` runs in the caller's transaction: it deletes the login's `credential` account, and only if there was one, its sessions in the gym, and audits `auth.password_removed` (no `before` or `after`); it returns whether it removed anything. A staff invitation or role grant calls it outside password mode. `auth_account` is visible only to the gym scope on this pool, which the account service exposes as `forGym`. Accepting a staff or portal invitation (`invitations.ts`, `portal-invitations.ts`) in password mode for a login that already has a password reserves the same `/sign-in/email` slot before verifying (no gym scope; a refused slot is `rate_limited`, verifies nothing and leaves the token live), keeps it on a wrong password or a failed transaction, and releases it once the acceptance commits; a login with no password reserves nothing.

Before dispatching CLI commands, initialize the database and call `configureAuthCli({ resolveGymId, smtpConfigured })` with the single-gym resolver; `core/runtime.ts` does this for `gym-app`. `gym-app auth reset-password <email>` prompts for a hidden password twice, requires a current owner, revokes every session and audits as the system, then clears that account's password and login-link windows (address limits stay in effect). No password is accepted in command arguments or environment variables. `gym-app auth change-email <current-email> <new-email>` moves a current owner's login to a new address at once (server access is the proof): it refuses an address another login uses, ends every session of the login, unlinks Google, and audits `auth.email_changed` as the system. Both commands need `TENANCY=single`.

Sign-in email changes (`email-change.ts`, `createEmailChangeService({ config })`) serve the account page's routes (`areas/staff/auth.account.ts`). They are offered only in `single` tenancy, because in `multi` mode one `auth_user` address belongs to every gym the login is in. A session alone never moves the login: `request` first proves it. Where the login has a `credential` password and the route says password sign-in is on for the gym (`passwordLogin`, as for the password change), it needs `currentPassword`, checked under the password sign-in account window (`reserveAccountAttempt` on `/sign-in/email` for the login's address, no gym scope, as `changeOwnPassword`): a missing one is a 400 (`currentPassword: ['required']`) before any attempt is counted, a wrong one is a 400 (`['wrong_password']`) that keeps its attempt, both record and send nothing, and a right one releases its attempt. Otherwise the proof is a link to the current address: the row is written with stage `current`, and only the current address gets an email, its link (`renderEmailChangeProofLink`, naming the new address masked). Opening that link (`confirm`) checks the login still has the old address, swaps the row for a stage `new` row with a fresh token and a new hour, audits `auth.email_change_proved`, and sends the new address its link or in-use notice as below; it never applies the change, and a failed send deletes the new row. The account summary says which proof the page asks for (`emailChangeProof`) and which link a pending change waits for (`awaiting`). Either way, `request` then checks the login's limit (`emailChangeLimit`, five an hour, counted in `auth_rate_limit` under the login's ID), then in one gym transaction locks the login, refuses its own address, replaces the login's outstanding change, stores a SHA-256 digest of a random 256-bit token in `auth_verification` (identifier `email-change:<gym>:<digest>`, value the login, the asking session, both addresses and the stage, a row without one reading as `new`; the portal columns stay null) for one hour, and audits `auth.email_change_requested`.

With the password proof, after the commit it sends the link (`/account-email#<token>` on the gym's canonical origin, from the injected `EmailChangeMail`) to a free address, or a short in-use notice without a link to an occupied address. Both cases return the same success response and record the same pending summary, so neither endpoint reveals another login. A failed send deletes the row. The old address also gets a request-time notice naming the new one only masked (`maskAddress`), including when delivery to the new address fails; a failed old-address notice is logged and does not withdraw a successfully sent link.

`confirm` finds the row only under the resolved gym's prefix, refuses an expired one, and refuses a request whose session is another login's; then it locks the row and the login, checks that the login still has the old address and that no other login took the new one (409 with `newEmail: ['email_in_use']`), sets the address and marks it verified, deletes the login's Google `auth_account` rows, deletes its other sessions in the gym (the asking session stays), deletes its change rows and audits `auth.email_changed` (`after`: whether Google was unlinked and how many sessions ended; no addresses), all in that transaction. The old address then gets another notice naming the new one masked; a failed notice is logged and doesn't undo the change. The hourly verification sweep deletes expired change rows with the install's other expired rows. `summary` reads the login's address, whether it has a password or a Google account, and its unexpired pending change for the page. Google is unlinked because it was linked for the old address: Better Auth joins a Google account to a login by a matching verified address, so the new address's Google account links again on its first sign-in.

Portal sessions store their chosen household in `auth_session.household_id` through `createPortalSessionStore` (`portal-sessions.ts`), which checks the user's household link in the same transaction and audits the choice. It is a preference, not a grant: the portal principal loader checks it against the user's current household links on every request. Portal invitations (`portal-invitations.ts`) store hashed, gym-bound tokens for a household login that is created only on acceptance. Their `auth_verification` rows also carry `gym_id`, `household_id`, `user_id` and `scope` (the binding's `payer` or `member`), which only this module sets (Better Auth's own rows, whose values aren't JSON, leave them null); partial indexes serve the lookups, and the identifier's gym prefix is still checked. Migrations 0013 and 0014 backfill them for invitations a process on an earlier release wrote. `outstanding` lists one household's unexpired invitations for staff (gym-scoped, never the token), `withPayerInvitations` runs a read in one gym transaction on this pool with a condition for households with an unexpired payer invitation, which the caller can limit to invitations issued after a point it names (the dashboard's confirmation shortlist leaves out a household whose invitation was issued at or after its latest confirmation request, in the same query), and `revoke` deletes one in a transaction that also runs the caller's audit. `expire` deletes a gym's expired invitations and claim holds in batches; `createPortalInvitationExpiryJobs` (`areas/members/household-users.invitations.ts`) runs it hourly for each gym. `sweepExpired` deletes the install's other expired verification rows (magic links, staff invitations), once an hour for the whole install: `registerVerificationSweep` registers it as a system job, which the runtime schedules. Better Auth's own cleanup is off (`service.ts`): it deleted every expired row on each sign-in, so expired invitations went before their invitees could be removed. Better Auth still refuses an expired token itself. Revoking and expiry also delete the invitee identity an invitation provisioned when it has no account and no other invitation row or claim hold. Identities with an account or a link in this gym are filtered out first and never locked; the rest are locked in ID order and checked again in the delete: links, staff roles and history in any gym keep an identity through their foreign keys, which bypass row-level security, so the lock and the delete run in a savepoint, a refused batch releases its locks, and it is halved until each held identity stands alone. `removeGymInvitees` runs the same cleanup in the system transaction that deletes a gym (`areas/settings/gym-delete.ts`), before the gym's cascade would take its invitation rows. `createPortalClaimCodes(AUTH_SECRET)` signs the stateless, one-hour claim codes carried by passwordless claim callbacks; completion requires the signed-in session of the user the code names. A passwordless onboarding claim also writes a hold (`holdClaim`: a `portal-claim:<gym>:<link>` row with the same columns) that lasts as long as its code, so the cleanup keeps the identity while the claim is pending, even if an invitation for the same address is revoked or expires meanwhile; asking again replaces it, completion (`completeOnboarding`) deletes it, and `expire` sweeps an abandoned one with the identity it kept. Completion locks the user after the onboarding link and the hold, so a user that is gone anyway answers 404 (restart from the onboarding link).

What Better Auth hands its logger goes to the application log (`library-log.ts`, `core/log.ts`), as `auth.library_warning` and `auth.library_error` lines. A line keeps the library's message with email addresses replaced by `[address]`, a query's bound parameters removed and the rest cut to 300 characters, and describes the first error by name, code, query text with placeholders and stack frames. Every other argument is dropped and counted in `dropped`. An error other than an API error that a routed endpoint throws (a failed query, a mail error) skips both: `onAPIError.throw` makes Better Auth's router reject instead of writing it raw to the console, and `routed` in `service.ts` logs it as `auth.handler_error` with the path and the error described as above (never its message, which can quote a bound address), then answers the router's bare 500. The library then skips its own logging of an internal-error API error as well, so `routed` also logs a 500 the router answers, as `auth.handler_error` with the path and status.
