# Link campaigns

Campaigns create an immutable recipient set using the signed-link service. The API supports all four link purposes; the admin page creates onboarding and card update campaigns. Every route requires `links.send`. Responses contain metadata only. Local creation limits are 2,000 recipients, a 120-character name, ten increasing reminder days from 1 to 365, and expiry within 90 days; the shared contract still needs the same bounds.

Progress partitions existing `signed_links` rows: used, revoked, expired, then pending. `completedAt` is the latest `usedAt` when every recipient completed, derived on each read. **Webhook-only completion:** Checkout and its setup/payment intent carry the immutable link ID; `billing.card_setup.started` / `billing.checkout.started` persist `{ sessionId }` against that link. After recording a card or payment, webhook dispatch awaits the shared signed-link completion checks before marking the event processed. Setup and payment-intent events locate Checkout only through that audit association. Closing the tab therefore still completes a payment/card link within the webhook cycle, and campaign reads and reminders immediately reflect it. Token rotation during Checkout preserves the association. An existing card alone never completes a campaign; onboarding still waits for current household waivers. Revoked and expired links remain refused, and replay or a concurrent browser check consumes once. Events without link metadata retain their existing payment/card behavior.

A successful payment intent can arrive while its correctly associated Checkout still appears open. Dispatch records the payment without an error and leaves the link pending until the session-completed event arrives. Missing associations and gym/link mismatches remain errors. A second pay link takes over an abandoned, link-tagged invoice Checkout only after provider-confirmed expiry and locked renewal; payment winning that race returns a conflict. The payment webhook completes only its associated link, so another pay link for that invoice stays pending. Untagged sessions remain shared.

Browser return uses the same completion checks for tagged sessions. Untagged sessions retain their original checks: the invoice is paid, partially refunded or refunded, or setup is complete for the gym and household customer with an unrevoked recorded card. No start association is required for these older sessions; onboarding still requires current household waivers. The runtime lets link routes resolve their own bearer after normal session loading. The browser checks immediately and retries after waits of 1, 2, 3, 4 and 5 seconds, showing a confirming status and offering manual checking after exhaustion. It can complete onboarding after its waivers are signed. Waiver signing is not retried.

Creation enqueues one `links.campaigns.publish` job immediately after committing the campaign, keyed by `<campaignId>:initial`. The request does no per-recipient queue publication. The publisher queues recipient sends and writes `delivery_queued` audits in batches of up to 100 per transaction. A crash before a batch audit commits is safe: stable per-recipient keys prevent duplicate sends while the publisher retry or hourly scan repairs publication. If publishing the job fails, `enqueue_failed` is audited and creation still returns the committed campaign. The hourly scan (`7 * * * *`) repairs interrupted publication and sends reminders within the hour after 09:00 gym-local. A grouped query selects only campaigns with pending, unexpired links; one audit query per campaign excludes reserved or published occurrences before enqueueing. After downtime only the latest due reminder is queued. An empty schedule disables automatic reminders. Stable `<linkId>:<occurrence>` keys and publication audits avoid new recipient jobs every day. Ordinary pre-reservation failures receive the queue's eight attempts. The Jobs interface cannot inspect or requeue an exhausted job; a later manual or scheduled occurrence is required once those attempts are exhausted. Recurring scan-job retention remains the queue owner's responsibility.

Both queue selection and locked delivery reservation read `billing.card_setup.started` and `billing.checkout.started` for the link. A start audit less than 24 hours old blocks all sends, preserving the credential in the Checkout return receipt. A queue-time block writes no publication audit, so the scan can catch up after 24 hours if the occurrence is still current. If Checkout starts after publication, the send logs `link_campaign.delivery_deferred` and drops that occurrence without rotating or reserving; the next scheduled or manual reminder covers it. These two Checkout actions use the same audit index.

When a queued send finds member emails disabled, it logs `link_campaign.delivery_skipped` with reason `member_emails_disabled` and completes without retries, reservation, or token changes. That published occurrence is skipped; later scheduled/manual reminders can send when enabled again. The shared delivery still rechecks the switch at the last moment and restores the old hash after suppression.

Each delivery rechecks link state, rotates the hash on the same recipient row without extending expiry, and calls `deliverSignedLink`. The shared delivery still validates the trusted origin, recipient preferences and persisted member-email switch immediately before sending. Campaigns observe that existing transport invocation to distinguish pre-send failures, suppressed results and transport exceptions. No separate SMTP or Stripe customer creation path is introduced.

A definite non-send restores the previous hash conditionally, only while the current hash is still this attempt's hash. Opt-out, undeliverability, missing/invalid email, switch suppression, and a non-sent transport result leave the earlier email usable. Trusted-origin/preparation failures cancel before rotation and can retry normally. A transport throw is classified with `deliveryAcceptance` (`infra/email/README.md`). A `not_accepted` DeliveryError proves no recipient got the email: the earlier hash is restored, `link_campaign.delivery_not_accepted` and `link_campaign.delivery_released` (naming the reservation) are written, and the error is rethrown so the send job retries within its eight attempts. Any other throw, including an `unknown` DeliveryError or an unclassified error, is ambiguous: keep the new hash because the email may have arrived, write `delivery_uncertain`, and do not replay that occurrence. An initial ambiguous failure with no scheduled reminders needs a later staff reminder.

A row-locked audit reservation permits at most one transport attempt per recipient and occurrence, and reserved/sent actions share a limit of one attempt per gym-local day across initial, scheduled and manual sends. Each reservation audit carries a reservation ID. Suppressed and uncertain attempts consume their reservation; a `delivery_released` audit with the same ID returns it, so a retry after a definite non-send can reserve the same occurrence on the same day. `link_campaign.delivery_sent`, `delivery_uncertain`, `delivery_not_accepted`, `delivery_suppressed` and `delivery_cancelled` describe outcomes without PII or credentials. Pending means incomplete, not proof of delivery. Successful reminders replace the earlier credential; uncertain reminders may also replace it.

**Audit records are correctness state:** duplicate prevention depends on `link_campaign.delivery_reserved`, `link_campaign.delivery_released`, `link_campaign.delivery_sent` and `link_campaign.delivery_queued`. Any future audit retention must retain these at least until the link expires, and must keep the two Checkout-start actions for at least their 24-hour hold (or until link expiry). Lookups filter gym, action and link target IDs, matching the existing `audit_events_gym_action_target_idx` on `(gym_id, action, target_id)`; no migration is needed. Duplicate send callbacks check these records before Stripe lookup.

Customer matching uses only gym-tagged exact email matches from `Payments.findCustomerByEmail`. Matching is optional: an unavailable payments resolver or a failed lookup writes a PII-free `link_campaign.customer_match_failed` audit with the campaign and occurrence, then delivery continues. Delivery errors keep their existing handling; a successfully sent occurrence is not sent again on replay. Existing IDs, changed addresses, ambiguous results, customers linked to another household, and customer-creation reservations are preserved under the household lock and existing uniqueness constraint. **Untagged customers from another system are not automatically matched or adopted**, even with the same email. Their existing cards will not be reused automatically, and opening a link can create another customer lazily. Explicit staff-confirmed adoption requires a payments lookup and recipient/confirmation contract change; email alone is not proof of ownership.

The editor's "Needs a card" filter uses the existing gym-scoped billing payment-method list, checks every needed page for an unrevoked card, and limits concurrent requests to four. It runs only on demand and reports lookup failures instead of assuming missing cards. "Select matching" adds to the selection across searches; filters preserve selections.

Composition calls `configureCampaigns(createCampaignsService({ jobs, clock, delivery, paymentsFor }))` using the existing per-gym signed-link delivery and payments resolver. Routes and jobs are exported through the area barrels. Tests cover the real registrations through `createApp` and assert unconfigured job handlers fail loudly. The registered consumers are `links.campaigns.publish`, `links.campaigns.scan`, and `links.campaigns.send`. The runtime injects the queue, clock, per-gym payments resolver and mail preparation; its composition test exercises publication, delivery and the hourly scan.

Run the screen check with Vite on an isolated port and `node apps/web/src/features/campaigns/mobile-check.mjs http://127.0.0.1:5197` using the pinned Node version and existing `e2e` dependencies. It checks 360px and desktop layouts, the card filter, labelled controls, 44px targets and axe accessibility.
