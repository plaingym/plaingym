# Link campaigns

Campaigns create their recipient set using the signed-link service; sends and reminders never add recipients, but a staff-created link that names the campaign does. The API supports all four link purposes; the admin page creates onboarding and card update campaigns. Every route requires `links.send`; the "Needs a card" list also requires `billing.read`. Responses contain metadata only. Creation limits are shared by the contract, service and editor: 2,000 recipients, a 120-character name, ten increasing reminder days from 1 to 365, and expiry within 90 days. Static bounds are in the contract schemas; relative expiry uses the service's injected clock and the editor's current time.

Progress partitions existing `signed_links` rows: used, revoked, expired, then pending. The database counts it with two grouped subqueries joined in one statement per page of campaigns (every link with its uses and latest use, then the unused links that are revoked or expired), so a read returns a row per campaign, not its links (`campaigns.model.ts`). `completedAt` is the latest `usedAt` when every recipient completed. Each completion path (Checkout/browser and webhook, waiver, or service completion) persists it in `link_campaigns.completed_at` under the campaign row lock and audits completion in the same transaction as link use. Adding recipients clears the stored completion. Reads still derive the value from their recipient snapshot. Recipient lists filter by state and page with `LIMIT`/`OFFSET` in SQL, in link ID order, with the page and its total joined in one statement, including empty pages. Both progress and recipient counts therefore use one database snapshot. Migration 0018 adds `signed_links_campaign_idx` on `(gym_id, campaign_id, id)` for these reads and the sends. **Webhook-only completion:** Checkout and its setup/payment intent carry the immutable link ID; `billing.card_setup.started` / `billing.checkout.started` persist `{ sessionId }` against that link. After recording a card or payment, webhook dispatch awaits the shared signed-link completion checks before marking the event processed. Setup and payment-intent events locate Checkout only through that audit association. Closing the tab therefore still completes a payment/card link within the webhook cycle, and campaign reads and reminders immediately reflect it. Token rotation during Checkout preserves the association. An existing card alone never completes a campaign; onboarding still waits for current household waivers. Revoked and expired links remain refused, and replay or a concurrent browser check consumes once. Events without link metadata retain their existing payment/card behavior.

A successful payment intent can arrive while its correctly associated Checkout still appears open. Dispatch records the payment without an error and leaves the link pending until the session-completed event arrives. Missing associations and gym/link mismatches remain errors. A second pay link takes over an abandoned, link-tagged invoice Checkout only after provider-confirmed expiry and locked renewal; payment winning that race returns a conflict. The payment webhook completes only its associated link, so another pay link for that invoice stays pending. Untagged sessions remain shared.

Browser return uses the same completion checks for tagged sessions. Untagged sessions retain their original checks: the invoice is paid, partially refunded or refunded, or setup is complete for the gym and household customer with an unrevoked recorded card. No start association is required for these older sessions; onboarding still requires current household waivers. The runtime lets link routes resolve their own bearer after normal session loading. The browser checks immediately and retries after waits of 1, 2, 3, 4 and 5 seconds, showing a confirming status and offering manual checking after exhaustion. It can complete onboarding after its waivers are signed. Waiver signing is not retried.

Creation stores the campaign and its links in one transaction through the signed-link service's `createSignedLinksIn` (`service.md`): the recipients' resources are checked with one query per kind and 500 IDs, then links and their audits go in as two multi-row inserts per 500 recipients, instead of a round trip per recipient. On a test database 2,000 recipients take about half a second; `campaigns.scale.test.ts` counts the insert statements rather than timing them, and for a 320-household campaign records each select's SQL and returned rows: a row per grouped progress count, a page of recipients, and filter pages with no Stripe call. A failure anywhere leaves no campaign, link or audit. Creation enqueues one `links.campaigns.publish` job immediately after committing the campaign, keyed by `<campaignId>:initial`. The request does no per-recipient queue publication. The publisher queues recipient sends and writes `delivery_queued` audits in batches of up to 100 per transaction. A crash before a batch audit commits is safe: stable per-recipient keys prevent duplicate sends while the publisher retry or hourly scan repairs publication. If publishing the job fails, `enqueue_failed` is audited and creation still returns the committed campaign. The hourly scan (`7 * * * *`) repairs interrupted publication and sends reminders within the hour after 09:00 gym-local. A grouped query selects only campaigns with pending, unexpired links; one audit query per campaign excludes reserved or published occurrences before enqueueing. After downtime only the latest due reminder is queued. An empty schedule disables automatic reminders. Stable `<linkId>:<occurrence>` keys and publication audits avoid new recipient jobs every day. Ordinary pre-reservation failures receive the queue's eight attempts. Once they are exhausted, the hourly scan finds the failed send through the queue's `failedJobs` and, on a later gym-local day than the one it failed on, resets that same job with `retryFailed` to run from 09:00 gym-local, audited as `link_campaign.delivery_retried`. This happens only while the occurrence is still the current one and unreserved; it creates no new job and never touches an active one, so a send is retried at most once a day. When the queue's retention is enabled (`infra/jobs/README.md`), it prunes finished scan and send jobs; it never touches these audits.

Both queue selection and locked delivery reservation read `billing.card_setup.started` and `billing.checkout.started` for the link. A start audit less than 24 hours old blocks all sends, preserving the credential in the Checkout return receipt. A queue-time block writes no publication audit, so the scan can catch up after 24 hours if the occurrence is still current. If Checkout starts after publication, the send logs `link_campaign.delivery_deferred` and drops that occurrence without rotating or reserving; the next scheduled or manual reminder covers it. These two Checkout actions use the same audit index.

When a queued send finds member emails disabled, it logs `link_campaign.delivery_skipped` with reason `member_emails_disabled` and completes without retries, reservation, or token changes. That published occurrence is skipped; later scheduled/manual reminders can send when enabled again. The shared delivery still rechecks the switch at the last moment and restores the old hash after suppression.

Each delivery calls `deliverSignedLink`, whose optional asynchronous `prepareSelected` callback receives the selected link-bearing or manual-payment mode before rendering and sending. The campaign callback rechecks link state and Checkout holds under the row lock, reserves the attempt, and rotates the hash only for a link-bearing email, without extending expiry. Manual-payment emails preserve the earlier credential. No transaction spans email delivery. Delivered tokens carry the public `campaign_` marker, so a rotated token opens the replaced page (`public/links/README.md`), and each campaign email containing a link says it replaces any earlier email for the same request. The shared delivery still validates the trusted origin, recipient preferences and persisted member-email switch immediately before sending. Campaigns observe that existing transport invocation to distinguish pre-send failures, suppressed results and transport exceptions. No separate SMTP or Stripe customer creation path is introduced.

A definite non-send restores the previous hash conditionally, only while the current hash is still this attempt's hash. Opt-out, undeliverability, missing/invalid email, switch suppression, and a non-sent transport result leave the earlier email usable. Trusted-origin/preparation failures cancel before rotation and can retry normally. A transport throw is classified with `deliveryAcceptance` (`infra/email/README.md`). A `not_accepted` DeliveryError proves no recipient got the email: the earlier hash is restored, `link_campaign.delivery_not_accepted` and `link_campaign.delivery_released` (naming the reservation) are written, and the error is rethrown so the send job retries within its eight attempts. Any other throw, including an `unknown` DeliveryError or an unclassified error, is ambiguous: keep the new hash because the email may have arrived, write `delivery_uncertain`, and do not replay that occurrence. An initial ambiguous failure with no scheduled reminders needs a later staff reminder.

A row-locked audit reservation permits at most one transport attempt per recipient and occurrence, and reserved/sent actions share a limit of one attempt per gym-local day across initial, scheduled and manual sends. Each reservation audit carries a reservation ID. Suppressed and uncertain attempts consume their reservation; a `delivery_released` audit with the same ID returns it, so a retry after a definite non-send can reserve the same occurrence on the same day. `link_campaign.delivery_sent`, `delivery_uncertain`, `delivery_not_accepted`, `delivery_suppressed` and `delivery_cancelled` describe outcomes without PII or credentials. Pending means incomplete, not proof of delivery. Successful link-bearing reminders replace the earlier credential; uncertain link-bearing reminders may also replace it. Campaign emails with a link explain this after the button, before the footer, in both HTML and plain text. Manual-payment emails have no link or replacement notice and do not replace the credential. Sent tokens have a public `campaign_` format marker followed by 32 random bytes, so an unresolvable marked token shows a static replaced-link page directing the reader to the newest email. That page reveals no resource or gym data and is identical for made-up tokens and other gyms; the marker is not authorization. Older unmarked links show general unavailable guidance that also mentions newer emails. No token history is retained.

**Audit records are correctness state:** duplicate prevention depends on `link_campaign.delivery_reserved`, `link_campaign.delivery_released`, `link_campaign.delivery_sent` and `link_campaign.delivery_queued`. Any future audit retention must retain these at least until the link expires, and must keep the two Checkout-start actions for at least their 24-hour hold (or until link expiry). Lookups filter gym, action and link target IDs, matching the existing `audit_events_gym_action_target_idx` on `(gym_id, action, target_id)`; no migration is needed. Duplicate send callbacks check these records before Stripe lookup.

Customer matching uses only gym-tagged exact email matches from `Payments.findCustomerByEmail`. Matching is optional: an unavailable payments resolver or a failed lookup writes a PII-free `link_campaign.customer_match_failed` audit with the campaign and occurrence, then delivery continues. Delivery errors keep their existing handling; a successfully sent occurrence is not sent again on replay. **A customer whose `household_id` metadata names another household is never a candidate**, whatever its email. A customer naming this household (made by a customer creation whose reply was lost) wins; otherwise the one customer naming no household is linked, and two or more are ambiguous and left alone. Existing IDs, changed addresses, ambiguous results and customers linked to another household are preserved under the household lock and existing uniqueness constraint. **Customers from another system, without this gym's `gym_id` tag, are not automatically matched or adopted**, even with the same email. Their existing cards will not be reused automatically, and opening a link can create another customer lazily. Explicit staff-confirmed adoption requires a payments lookup and recipient/confirmation contract change; email alone is not proof of ownership.

A customer-creation reservation (`customers.README.md`) holds off matching for its 15-minute lease, renewed by each retry of the creation; matching then makes no Stripe call. After the lease, matching first compares the reservation's request hash with the household's current details and creation generation. Changed details retain the hold on email-only matching for staff reconciliation, even after an earlier release. Once the creation lease ends, a lookup may still link an exact-email, gym-tagged customer whose metadata explicitly names this household; it never releases the changed-details reservation or falls back to an email-only candidate. With unchanged details, the email lookup checks for the customer the creation may have made: one naming this household is linked (`link_campaign.customer_matched` with `tagged: true`); if none does, matching writes `billing.customer.creation_released` (naming the reservation and the attempt whose lease ended) and goes on with the other candidates. A release only ends the hold on matching: a later creation still replays the reservation with its own key. Both checks are repeated under the household lock, so a creation retry or detail change during the lookup wins. Each lease read fetches the newest unlink, reservation, retry and release in one statement, at most four rows; these actions are written under the household lock, the read orders them by transaction start time, not lock order, and their generation/attempt references discard older events.

The editor's "Needs a card" filter calls `GET /api/link-campaign-households/needing-card` (`links.send` and `billing.read`), which lists the gym's households with no saved card that isn't removed, 100 IDs a page in ID order. Requests pass `after` (the previous page's last household ID), and responses return `pagination.nextAfter` or null. A card saved between pages cannot shift another household past the cursor. One query per page answers it from `payment_methods` (an anti-join on its `(gym_id, household_id, id)` key), so the editor sends a request per 100 households without a card instead of one per household, and nothing calls Stripe. That table is the gym's record of saved cards: the card webhooks (`checkout.session.completed`, `setup_intent.succeeded`, `payment_method.updated` and `payment_method.automatically_updated`) and staff card removal keep it current, and the charge runner charges only cards recorded there. A card attached in Stripe outside these flows isn't recorded, so its household shows as needing a card, as the runner would treat it. The filter runs only on demand and reports lookup failures instead of assuming missing cards. "Select matching" adds to the selection across searches; filters preserve selections.

Changed-details holds write `link_campaign.customer_match_held` once per creation reservation under the household lock; its payload contains only the reservation ID. Recipient responses expose `customerMatchHeld`, computed from current household and lease state with two bounded reads per page, and true only for pending recipients of purposes that match customers (not `sign_waiver`). Staff see a reconciliation notice on those recipients. The editor interpolates limit messages from `campaignLimits`, and bulk creation rejects duplicate resource IDs after lowercasing them.

Composition calls `configureCampaigns(createCampaignsService({ jobs, clock, delivery, paymentsFor }))`, where `jobs` also implements `JobRecovery` (the Postgres queue does), using the existing per-gym signed-link delivery and payments resolver. Routes and jobs are exported through the area barrels. Tests cover the real registrations through `createApp` and assert unconfigured job handlers fail loudly. The registered consumers are `links.campaigns.publish`, `links.campaigns.scan`, and `links.campaigns.send`; all three register in the batch lane (`infra/jobs/README.md`), so a campaign's up to 2,000 sends never hold up the gym's webhooks and notices. The runtime injects the queue, clock, per-gym payments resolver and mail preparation; its composition test exercises publication, delivery and the hourly scan.

Run the screen check with Vite on an isolated port and `node apps/web/src/features/campaigns/mobile-check.mjs http://127.0.0.1:5197` using the pinned Node version and existing `e2e` dependencies. It checks 360px and desktop layouts, the card filter, labelled controls, 44px targets and axe accessibility.

Pay-invoice delivery checks invoice status and amount before reserving a credential. Closed and zero invoices are skipped without email. A positive amount below the card minimum or off its currency step receives a manual-payment notice with no URL and a `link_campaign.delivery_manual` audit, rather than a sent-link audit. Manual and skipped deliveries never rotate the hash. If no earlier message may have disclosed the credential, delivery revokes that undisclosed link and stops its reminders. Otherwise it preserves the earlier credential (including an uncertain or interrupted link delivery), and occurrence reservations prevent repeat notices. A zero amount never reaches the card minimum/step check. Checkout reservation audits store the invoice's exact `checkoutExpiresAt`; a retry finds that reservation by expiry rather than by audit time.
