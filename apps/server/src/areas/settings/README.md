General settings and booking rules use the gym revision for compare-and-set updates. Currency changes lock the gym row and are rejected when plans, charge types, memberships, or invoices exist; currency foreign keys also protect concurrent inserts. Responses and audits use the same explicit safe projection and exclude credentials and opaque settings.

The module helpers take the existing server registry and inspect request context or job gym settings at execution time. The website definition remains a stub; core does not import it.

Gym creation reserves the gym and primary domain in an audited system transaction through `core/tenancy-bootstrap.ts`. The new gym ID scopes the audit in that transaction. A retry must match the original slug, hostname, owner email, name, timezone, and currency; unrelated existing gyms are rejected.

After reservation commits, `createOwnerService` provisions the identity and owner role together, then sends a gym-bound magic link outside the transaction. The default CLI uses this service directly and returns gym/user IDs and delivery status. A failure leaves a reservation that an identical retry can resume; uniqueness constraints prevent duplicate identities or owner roles. Delivery retries may resend a link. Staff invitation management is a separate service.

Email, Stripe and backups after setup (`integrations.ts`, `/api/settings/integrations`, `integrations.manage`, owners only) reuse the setup steps' parts and the gym revision. Nothing they return, audit or log holds an SMTP password, Stripe key, webhook signing secret, storage credential or private key; only the key-creation response shows the new private key, once. Email saves only after its test message is accepted (on a multi-gym install, only to SMTP ports 25, 465, 587 or 2525, so a tenant can't probe other services), and removal is refused while it would leave the signed-in owner no sign-in method. A new Stripe key is refused for another account or mode once the gym has Stripe customers, cards or card payments: after the permission probe, the new key must read at least one of up to seven of them (customers, PaymentIntents, charges or payment methods, all readable with the setup permissions); a 404 on every one means another account, and one stale or imported ID can't block a change. A key in the other mode is refused (`mode_locked`), with one way out: from test to live, a request with `clearTestData: true` skips the account check and, once the live key has connected, clears the gym's test-mode references inside the save's transaction. It first locks the open and past-due invoices, which the charge runner locks to reserve an attempt, and is refused with `payments_in_progress` while an attempt or refund is pending. It clears only what the test key made: a household's `stripe_customer_id` when an audit shows the app linked that customer (`billing.customer.linked` from the customers service, or `link_campaign.customer_matched` naming it), audited as `billing.customer.unlinked`, as it does for each household with a customer creation reservation (one may be in flight with the test key); the unlink starts a new creation generation (`areas/billing/customers.README.md`). It revokes the cards saved through Stripe, and an imported card only when its household's customer is cleared. An import writes Stripe IDs without asking Stripe, so they may be the gym's live ones: imported customer IDs and their cards stay, and `testData` lists them as kept (`importedCustomers`, `importedCards`). It drops the Checkout sessions and reservations of open and past-due invoices (paid and void ones keep their completed session's ID), closes action-needed attempts as failed, and marks the card payments since the last switch as test with the reference `Stripe test mode` (`stripeTestPaymentReference`; card payments otherwise never have one), all in one `integrations.stripe_test_cleared` audit with the counts and the marked payment IDs; invoices, refunds and attempts stay. After the commit, the old test key expires the dropped Checkout and card setup sessions and cancels the action-needed PaymentIntents (the request waits at most 10 seconds for them; the rest finish after it, and failures are logged), and `retireStale` removes the old test endpoint. That audit is the gym's test-data boundary: attempts, card payments and cards recorded before it no longer tie the gym to an account. Live to test stays refused while live references exist. While the gym has no Stripe settings and only imported customer IDs (no attempts, card payments or cards: `importedCustomersOnly`), any account's key is accepted; with a live key, Checkout later replaces an ID the account can't read (with a test key it refuses instead, since a live customer looks missing to a test key). A refund of a payment marked `Stripe test mode` is refused (`test_payment`): the live key can't refund it. GET returns `testData` (what the switch would clear) while the gym is in test mode with references. Backups exist only in single-gym mode outside demo mode: a new destination is listed with its credentials first, then it and a new key wait in `gyms.settings.integrations.backup` (credentials encrypted) while snapshots keep the current ones, and activate only when the pasted private key matches; the blob key is kept, since snapshot reference lists are authenticated with it and a new one would stop pruning. Confirming queues one snapshot (`requestSnapshot`). In demo mode the section is read-only.

Email uses the gym's own SMTP settings first and the install's `SMTP_*` otherwise (`smtp.ts`). Setup stores a gym's settings with `encryptSmtpConfig` in `gyms.smtp_config_encrypted` as `{ host, port, security, from, username, password }`; `createSmtpResolver` decrypts them for login links and member email, and they never appear in responses or logs.
