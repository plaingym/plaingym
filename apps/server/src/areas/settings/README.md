General settings and booking rules use the gym revision for compare-and-set updates. Currency changes lock the gym row and are rejected when plans, charge types, memberships, or invoices exist; currency foreign keys also protect concurrent inserts. Responses and audits use the same explicit safe projection and exclude credentials and opaque settings.

The module helpers take the existing server registry and inspect request context or job gym settings at execution time. The website definition remains a stub; core does not import it.

Gym creation reserves the gym and primary domain in an audited system transaction through `core/tenancy-bootstrap.ts`. The new gym ID scopes the audit in that transaction. A retry must match the original slug, hostname, owner email, name, timezone, and currency; unrelated existing gyms are rejected.

After reservation commits, `createOwnerService` provisions the identity and owner role together, then sends a gym-bound magic link outside the transaction. The default CLI uses this service directly and returns gym/user IDs and delivery status. A failure leaves a reservation that an identical retry can resume; uniqueness constraints prevent duplicate identities or owner roles. Delivery retries may resend a link. Staff invitation management is a separate service.

Email, Stripe and backups after setup (`integrations.ts`, `/api/settings/integrations`, `integrations.manage`, owners only) reuse the setup steps' parts and the gym revision. Nothing they return, audit or log holds an SMTP password, Stripe key, webhook signing secret, storage credential or private key; only the key-creation response shows the new private key, once. Email saves only after its test message is accepted (on a multi-gym install, only to SMTP ports 25, 465, 587 or 2525, so a tenant can't probe other services), and removal is refused while it would leave the signed-in owner no sign-in method. A new Stripe key is refused for another account or mode once the gym has Stripe customers, cards or card payments: after the permission probe, the new key must read at least one of up to seven of them (customers, PaymentIntents, charges or payment methods, all readable with the setup permissions); a 404 on every one means another account, and one stale or imported ID can't block a change. This also refuses a switch from test to live once test-mode customers exist. Backups exist only in single-gym mode outside demo mode: a new destination is listed with its credentials first, then it and a new key wait in `gyms.settings.integrations.backup` (credentials encrypted) while snapshots keep the current ones, and activate only when the pasted private key matches; the blob key is kept, since snapshot reference lists are authenticated with it and a new one would stop pruning. Confirming queues one snapshot (`requestSnapshot`). In demo mode the section is read-only.

Email uses the gym's own SMTP settings first and the install's `SMTP_*` otherwise (`smtp.ts`). Setup stores a gym's settings with `encryptSmtpConfig` in `gyms.smtp_config_encrypted` as `{ host, port, security, from, username, password }`; `createSmtpResolver` decrypts them for login links and member email, and they never appear in responses or logs.
