Malformed install Google variables are returned as `installProblem` only in single
mode. A stored gym client remains in use and Health warns about the ignored
variables. Multi mode keeps the startup log only.

SMTP resolution also treats unreadable stored credentials as unconfigured, with
the same redacted logging; login and Google removal then use install SMTP if
available. Email removal still counts Google for the gym rather than checking the
owner's linked identity. The Email section states this and asks the owner to try
Google first. Each submitted Settings test writes `integrations.email_tested` with
`test: 'sent' | 'failed'`, without credentials or recipients, even when it fails
and the saved settings stay unchanged. Operator-managed refusals reload the
integrations and show the operator notice in place of the editable forms.

`checkIntegrationsEnvironment(mode, env)` exports the policy validation for early
boot: the runtime calls it in `prepare()` before any database connection is opened,
so an unknown `GYM_INTEGRATIONS` value stops the start there.

Unreadable Google clients are reported as `source: 'none'` and `unreadable: true`, with no stored ID or secret flag and both removal and replacement available. They do not count as a way in when removing email settings. Google reads and settings SMTP reads share `unreadable-secret.ts`: it remembers the last failed ciphertext per secret class, gym and encryption-key object, logging one redacted error until the stored value changes; no decrypted value is cached. Google audit source values still describe the stored configuration.

Both setup and Settings check a backup destination before generating a key using `backup-destination.ts`: list an unused snapshot prefix, then write, read back and delete a unique probe blob (`blobs/probe-<uuid>`), so credentials limited to the `snapshots/` and `blobs/` prefixes snapshots use pass and ones that can't write there don't; a probe whose cleanup failed is an unreferenced blob, which pruning removes without stopping. A refusal returns `destination: ['unreachable']` without saving anything. Backup status uses only complete snapshots at the current destination whose authenticated references name the current recipient; legacy reference lists without a recipient cannot establish that match.

General settings and booking rules use the gym revision for compare-and-set updates. Currency changes lock the gym row and are rejected when plans, charge types, class packs, discounts, memberships, or invoices exist; currency foreign keys also protect concurrent inserts. Responses and audits use the same explicit safe projection and exclude credentials and opaque settings.

The module helpers take the existing server registry and inspect request context or job gym settings at execution time. The website definition remains a stub; core does not import it.

A new timezone, in setup, in a general settings save and in `gyms create`, follows one shared rule (`gymTimezoneSchema`): spaces around it are dropped (a pasted ` America/Vancouver` is accepted in all three), then `UTC` or a region form that `Intl` knows, stored in its canonical case (Temporal's identifier), so `america/vancouver` is stored as `America/Vancouver`. Links are kept as given (`US/Pacific` stays `US/Pacific`), because `Intl` resolves current names to retired ones (`Asia/Kolkata` to `Asia/Calcutta`, `Europe/Kyiv` to `Europe/Kiev`). Abbreviations (`PST`, `CET`) and `Etc/GMT±N` (its sign is inverted, and a region form exists for every offset) are refused. The general settings request validates `timezone` with that rule. A general or retry-schedule save that fails validation is a 400 whose `details` name every refused field by its path (`timezone`, `name`, `address.country`), each with a code: `invalid_timezone` for the zone, `invalid_retry_days` for the retry schedule, and `invalid` for any other; a body that supplies no change names no field. The timezone is optional, and a save that leaves it out keeps the stored zone, whatever it is, as it was. A stored zone is never rewritten.

Gym creation reserves the gym and primary domain in an audited system transaction through `core/tenancy-bootstrap.ts`. The new gym ID scopes the audit in that transaction. A retry must match the original slug, hostname, owner email, name, timezone, and currency; unrelated existing gyms are rejected.

After reservation commits, `createOwnerService` provisions the identity and owner role together, then sends a gym-bound magic link outside the transaction. The default CLI uses this service directly and returns gym/user IDs and delivery status. A failure leaves a reservation that an identical retry can resume; uniqueness constraints prevent duplicate identities or owner roles. Delivery retries may resend a link. Staff invitation management is a separate service.

Email, Stripe and backups after setup (`integrations.ts`, `/api/settings/integrations`, `integrations.manage`, owners only) reuse the setup steps' parts and the gym revision. Nothing they return, audit or log holds an SMTP password, Stripe key, webhook signing secret, storage credential or private key; only the key-creation response shows the new private key, once. Email saves only after its test message is accepted (on a multi-gym install, only to SMTP ports 25, 465, 587 or 2525, so a tenant can't probe other services), and removal is refused while it would leave the signed-in owner no sign-in method. A new Stripe key is refused for another account or mode once the gym has Stripe customers, cards or card payments: after the permission probe, the new key must read at least one of up to seven of them (customers, PaymentIntents, charges or payment methods, all readable with the setup permissions); a 404 on every one means another account, and one stale or imported ID can't block a change. A key in the other mode is refused (`mode_locked`), with one way out: from test to live, a request with `clearTestData: true` skips the account check and, once the live key has connected, clears the gym's test-mode references inside the save's transaction. It first locks the open and past-due invoices, which the charge runner locks to reserve an attempt, and is refused with `payments_in_progress` while an attempt or refund is pending. It clears only what the test key made: a household's `stripe_customer_id` when an audit shows the app linked that customer (`billing.customer.linked` from the customers service, or `link_campaign.customer_matched` naming it), audited as `billing.customer.unlinked`, as it does for each household with a customer creation reservation (one may be in flight with the test key); the unlink starts a new creation generation (`areas/billing/customers.README.md`). It revokes the cards saved through Stripe, and an imported card only when its household's customer is cleared. An import writes Stripe IDs without asking Stripe, so they may be the gym's live ones: imported customer IDs and their cards stay, and `testData` lists them as kept (`importedCustomers`, `importedCards`). It drops the Checkout sessions and reservations of open and past-due invoices (paid and void ones keep their completed session's ID), closes action-needed attempts as failed, and marks the card payments since the last switch as test with the reference `Stripe test mode` (`stripeTestPaymentReference`; card payments otherwise never have one), and closes the open disputes on the invoices of those payments (status `closed`, each audited as `billing.invoice.disputed` with `reason: 'stripe_test_cleared'`; the live key can't read or answer them), all in one `integrations.stripe_test_cleared` audit with the counts and the marked payment and disputed invoice IDs; invoices, refunds and attempts stay. Work already running waits for the save on the gym row (`holdGymSettings`): a charge reservation that resolved its provider before the switch reserves nothing and resolves it again, a refund reserved meanwhile is refused once its payment is marked (`test_payment`), and the dispute writer leaves a marked payment's dispute unrecorded; a Stripe test-mode webhook event dispatched after the switch is finished with an audit and no Stripe call (`areas/billing/webhooks/inbox.md`). After the commit, the old test key expires the dropped Checkout and card setup sessions and cancels the action-needed PaymentIntents (the request waits at most 10 seconds for them; the rest finish after it, and failures are logged), and `retireStale` removes the old test endpoint. That audit is the gym's test-data boundary: attempts, card payments and cards recorded before it no longer tie the gym to an account. Live to test stays refused while live references exist. While the gym has no Stripe settings and only imported customer IDs (no attempts, card payments or cards: `importedCustomersOnly`), any account's key is accepted; with a live key, Checkout later replaces an ID the account can't read (with a test key it refuses instead, since a live customer looks missing to a test key). A refund of a payment marked `Stripe test mode` is refused (`test_payment`): the live key can't refund it. GET returns `testData` (what the switch would clear) while the gym is in test mode with references. Backups exist only in single-gym mode outside demo mode: a new destination passes the probe above with its credentials first, then it and a new key wait in `gyms.settings.integrations.backup` (credentials encrypted) while snapshots keep the current ones, and activate only when the pasted private key matches; the blob key is kept, since snapshot reference lists are authenticated with it and a new one would stop pruning. Confirming queues one snapshot (`requestSnapshot`). In demo mode the section is read-only.

On a multi-gym install email and payments are read-only for gym owners unless `GYM_INTEGRATIONS=gym` (`gymIntegrationsEditable` in `core/tenancy.ts`): GET reports it as `integrationsEditable`, and saving or removing email and saving a Stripe key answer 403 (`operator_managed`). Single-gym installs ignore the variable, and `integrationsEditable` is always true there.

Google sign-in (`/api/settings/integrations/google`, same permission and revision) stores the gym's own OAuth client encrypted in `gyms.google_config_encrypted` (`google-login.ts`, secret class `google_config`). GET returns the source (`install`, `gym` or `none`), whether the form is offered (`editable`), the stored client ID and only whether a secret is set; the secret is never returned, audited (`integrations.google_saved` and `integrations.google_removed` record only the source) or logged. A save first checks the revision, then asks Google's token endpoint about the client outside any transaction (`requireGoogleClient`, as setup does): a client Google refuses answers 400 with the reason `google_rejected` and nothing is stored, and the save's reply carries `check` (`accepted`, or `unknown` when Google couldn't be asked). GET reports malformed install `GOOGLE_*` variables as `installProblem` (the variable and the reason), and the Health page's `google_login` tile shows the same (`areas/health/status.providers.ts`). A save replaces both values; removal is refused (`only_sign_in`) while it would leave the signed-in owner neither email links nor a password of their own. `createGoogleClientResolver` decides the client per request: the install's `GOOGLE_*` variables win in either mode (saves are then refused with `install_configured`), a single-gym install otherwise uses the stored client, and multi-gym and demo installs ignore the column (saves answer 404). An unreadable stored client counts as none and is logged without its value.

Email uses the gym's own SMTP settings first and the install's `SMTP_*` otherwise (`smtp.ts`). Setup stores a gym's settings with `encryptSmtpConfig` in `gyms.smtp_config_encrypted` as `{ host, port, security, from, username, password }`; `createSmtpResolver` decrypts them for login links and member email, and they never appear in responses or logs. On a multi-gym install it marks a gym's own settings `publicHostOnly`, as the Settings test message does, so `SmtpEmail` connects only to a public address (`infra/email/README.md`). A refused host is a failed test, indistinguishable from a name that doesn't resolve. The install's `SMTP_*` are the operator's and aren't marked.
