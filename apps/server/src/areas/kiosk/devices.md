# Kiosk device authentication

The settings section registers devices, displays a random 256-bit bearer once, and revokes access. Only lowercase SHA-256 hashes enter the database. List/revoke responses and audits contain public device metadata only. Authentication checks revocation in a short gym-scoped transaction on every request; there is no token cache.

Integration: export `createKioskAuthMiddleware` from `devices.auth.ts`. After gym resolution, wrap the existing session middleware with `createKioskAuthMiddleware({ session, ...clientIpOptions })` as the app's session middleware. Alternatively dispatch this wrapper for `/api/kiosk/*` and the existing session middleware elsewhere. Do not run session middleware again after the wrapper: it replaces the principal. Preserve the app's CSRF, flood limiter, and route authorization middleware.

Only the exact POST contracts `lookup`, `checkinNamePin`, and `checkinQr` accept bearer authentication. Any other request with an Authorization header returns 404 when passed through this wrapper. Requests without that header delegate to the supplied session middleware, so staff can manage devices normally.

PIN lookup and name/PIN submission share independent per-device and per-client-address fixed-window limits (10 wrong PINs per minute each). An in-flight request reserves a slot before verification. The check-in service reports what each guess came to through `markKioskPinChecked`: `skipped` when the name matched no household or more than `maxCandidateHouseholds`, so no PIN was compared; `compared` for a wrong PIN (a name matching two households that share the PIN counts as wrong); `verified` when it matched exactly one household. A wrong PIN keeps its slot, and so does any successful response the service didn't report, so a handler that forgets to report fails closed. A verified PIN (even if standing sends the member to the front desk), a skipped check, and an invalid body or an error answered before any report each release only their own slot when the request completes. Earlier wrong PINs remain counted. The kiosk's answer is the same either way, so valid family/session selections and common names no longer exhaust the wrong-PIN budget. The budget itself still tells a name matching one to three households (it can run out) from one matching none or more (it can't), as the time taken by the PIN check already does; that costs a whole window's budget per name found, and each used-up budget is audited. QR requests do not consume PIN attempts. Client addresses use the core trusted-proxy resolver and its client key (an IPv6 /64 shares one budget; an IPv4-mapped address counts as its IPv4 address); arbitrary forwarding headers are ignored. Buckets are bounded: a full table evicts rather than refusing new devices or addresses, sparing buckets over their limit and the request's own (`RateBuckets` in `core/rate-limit.ts`).

When settled wrong PINs use up a device's budget or its client address's budget (in-flight attempts that later verify don't count), the middleware writes one `kiosk.device.pin_limit_reached` audit event, with the device whose wrong PIN used it up as the actor and target (`pinLimitReached`, which defaults to `createPinLimitAudit()` in `pin-limit.ts`). Each budget is reported once per window; `after.budgets` names the budgets used up (`device`, `address`, or both when one kiosk uses up both at once). An address budget runs out when several kiosks behind one address together make 10 wrong guesses, and it locks all of them out. A failure to record it is logged and never changes the kiosk's answer. `createPinLimitWidgetProvider()` adds a dashboard count, for staff with `kiosk_devices.manage`, of devices named by these events in the last 24 hours; it shows a zero count too. Other kiosks locked out by the same address budget aren't counted, since the limiter doesn't know which devices share an address. These limits are process-local, like the core flood limiter; multiple processes each enforce their own budget. Reuse one middleware instance, and pass the same trusted proxy configuration as the session and app limiters.

The check-in handlers themselves are supplied by their own kiosk parts. Middleware tests use contract-shaped handlers until those implementations are available.

The production runtime delegates `/api/links/*` to normal session loading so signed-link routes resolve their own bearer; every other path keeps this wrapper's device-token restrictions.

The production runtime mounts this wrapper ahead of session loading. Activity
updates `last_seen_at` at most once per minute using a conditional write; routine
authenticated requests do not add audit rows. Registration and revocation remain audited.
