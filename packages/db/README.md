# Database schema

Schema v1 contains 51 PostgreSQL tables. `src/schema/` is the source of truth;
`src/migrations/0001_schema_v1.sql` is generated by Drizzle. Migration
`0002_rank_colors.sql` adds nullable `ranks.color` with a six-digit hex check;
existing ranks keep null. Its journal entry and snapshot are numbered 0002.
Migration `0003_open_mat.sql` adds `kind` (`class` or `open_mat`, default `class`)
to class templates, class sessions and attendance, and `gyms.open_mat_counts_as_class`
(default false). It marks existing session-less kiosk and coach visits as open mat.
Migration `0004_occurrence_keys.sql` adds nullable `class_sessions.occurrence_starts_at`
(the start a template originally scheduled) with a unique `(gym_id, template_id,
occurrence_starts_at)` constraint, and backfills it from `starts_at` for existing
generated sessions. The earlier `(gym_id, template_id, starts_at)` constraint stays.
Migration `0005_import_run_state.sql` adds the gym-owned `import_runs`, `import_chunks`
and `export_runs` tables that hold import and export progress. Migration
`0006_membership_anniversary.sql` adds nullable `memberships.anniversary_on`, the
original anniversary of an annual membership; existing rows keep null.
Migration `0007_payment_method_processor_created_at.sql` adds nullable
`payment_methods.processor_created_at` for processor ordering of saved cards.
Migration `0008_audit_action_target.sql` adds `audit_events_gym_action_target_idx`
on `(gym_id, action, target_id)` for transition/outbox lookups; no data is rewritten.
Migration `0011_email_deliveries.sql` adds the gym-owned `email_deliveries` table: durable
send state (`sending`, `accepted`, `unknown`, `not_accepted`) per caller idempotency key, unique on
`(gym_id, key)`. It starts empty and its rows are never pruned (`infra/email/README.md`).
Migration `0022_email_delivery_commands.sql` adds its nullable `command_digest` and `command_result`
columns, set only on a send command's row; existing rows keep them null.
Migration `0012_job_schedule_cursors.sql` adds `job_schedule_cursors`, a system table with gym
access next to `jobs`: one row per gym and cron schedule, unique on `(gym_id, name)`, holding the
schedule's expression, timezone and latest enqueued occurrence. It starts empty; the scheduler seeds
each cursor from the existing job history on its first tick (`infra/jobs/README.md`).
Migration `0013_portal_invitation_columns.sql` adds nullable `gym_id` (cascading from `gyms`),
`household_id` and `user_id` (cascading from `auth_user`) to `auth_verification`, set only on portal
invitation rows, with partial indexes on `(gym_id, household_id, expires_at)` and `(user_id)`. It
backfills them from existing invitations' identifiers and JSON values; every other row (Better
Auth's own, whose values aren't JSON, and staff invitations) keeps null, as does an invitation whose
gym or invitee no longer exists. Upgrade tests outside this package import the helper as
`@plaingym/db/testing/database-upgrade`.
Migration `0014_portal_invitation_scope.sql` adds a nullable `scope` to `auth_verification`
(`payer` or `member`, checked), set only on portal invitation rows. It repeats 0013's guarded
backfill for invitations still missing a column: those a process on the release before 0013 wrote
after it ran (no gym, household or invitee), and those a process on the 0013 release wrote (no scope).
Migration `0015_refund_canceled.sql` widens `refunds_status_check` to allow `canceled`, for a refund
cancelled at the processor before it completed. Every existing row already satisfies the new check.
Migration `0016_drop_in_charge_type.sql` adds nullable `gyms.drop_in_charge_type_id`, the charge type
whose price the public drop-in page shows. Existing gyms keep null. It has no foreign key: one would
make the `gyms` and `charge_types` schema modules import each other, which breaks loading them in some
orders. Instead, the settings service accepts only a charge type visible under the gym's row-level
security, and the drop-in fee reader also matches it on `gym_id`, so a stale or foreign ID shows no fee.
Migration `0017_google_config.sql` adds nullable `gyms.google_config_encrypted`, a gym's own Google
OAuth client (secret class `google_config`). Existing gyms keep null, which leaves Google sign-in to
the install's `GOOGLE_*` variables as before.
Migration `0018_signed_links_campaign_index.sql` adds `signed_links_campaign_idx` on
`(gym_id, campaign_id, id)`, for campaign progress counts, recipient pages and sends. It changes no data.
Migration `0020_intake_rate_limits.sql` adds `intake_rate_limits`, a system-only table of public intake
counters, unique on `(gym_id, route_key, client_key, window_start)` with nulls not distinct, because a
null gym means an install-level request. It starts empty and changes no existing data.
Migration `0021_refund_tagged_at.sql` adds nullable `refunds.tagged_at`, set on a new card refund
reservation whose processor refund carries the row ID. Existing rows stay null, with no backfill, and
keep matching a processor refund as they did before.
Migration `0024_announcements.sql` adds `announcements`, `announcement_recipients` and
`announcement_opt_outs`, all gym-owned with forced RLS and composite references between
gym-owned rows. Announcements store the sending user, bounded subject/body, status/program
audience, recipient count and completion state. Recipient rows store only member references,
send state and a checked safe reason (`opt_out`, `undeliverable`, `disabled`, `anonymized`,
`ineligible`, `missing_email`, `duplicate_address`, `not_accepted`, `unknown`), never copied
addresses, bodies or SMTP responses. Their send scan index leads with gym, announcement,
state and ID; each member appears once per announcement. Opt-outs are unique per gym/member
and separate from the member's transactional-email flag. Announcement history and opt-outs
are gym export datasets; recipient rows are install-local delivery run state, excluded from
exports like `email_deliveries`. The migration also widens the signed-link database checks
for `unsubscribe`: a member in the link's household is required and an invoice is forbidden.
The application purpose union and public preference handlers support this purpose;
staff link lists and send actions exclude it.

Migration `0025_announcement_scale.sql` adds a required `send_generation` to announcements,
backfilled from each existing ID and unique per gym. New IDs are generated separately by
the app. The generation is install-local send state, excluded from announcement CSV history.
It indexes `email_deliveries (gym_id, command_digest)` and
`announcement_recipients (gym_id, member_id)`, and checks lifecycle pairs: sent announcements
have `completed_at`; sending announcements do not. Failed/skipped recipients require a
reason; pending/sent recipients do not have one. Before adding the checks, it normalizes
legacy pairs: missing sent completion times use `created_at`, sending completion times are
cleared, missing failed/skipped reasons become `unknown`/`ineligible`, and pending/sent
reasons are cleared. Message content, recipients and outcome states are preserved.

Migration `0026_leads.sql` adds two empty gym-owned tables, `leads` and
`lead_contacts`, without changing existing rows. Leads are unique per gym/member
with nullable source, default stage `new`, revision, follow-up date and lifecycle
timestamps. Checks constrain sources and stages, require the corresponding
timestamp for `won` and `lost`, and bound lost reasons to 500 characters.
Contacts reference a lead in the same gym, record their staff author and channel,
and limit notes to 2,000 characters. Both have forced gym RLS; member and lead
references use `NO ACTION`. Stage and open follow-up indexes support lead reads;
contact history is indexed by gym, lead and occurrence time. Both are exported.
No backfill or automatic lead deletion is performed.

Migration `0027_class_packs.sql` adds four empty gym-owned tables: `class_packs`,
`class_pack_tax_rates`, `class_pack_sales` and `class_credit_entries`. Packs have
1–100 credits and optional expiry of 1–3,650 days. Sales snapshot these terms,
keep the invoice's household, and reference the member without household so a
household move does not rewrite purchase history. Ledger lots and sales must
belong to the same gym and member. Partial unique indexes deduplicate grants,
uses, reversals, expiry and adjustments, including lot-opening adjustments.
The ledger's only app-updatable column is `reason`; app cannot delete its rows.
An adjustment reason is required; app may later clear it to the empty string.
All four tables are included in gym exports. This migration issues no credits.

Keep the SQL file name, journal tag, index and snapshot name aligned.

`databaseCode(error)` returns a database error's SQLSTATE code, also when Drizzle wraps the driver
error as a cause.

Run generation from this package with `pnpm exec drizzle-kit generate --name <name>`.
Commit the generated SQL and metadata together. Add an SPDX SQL comment to generated
SQL files. Never edit a table definition directly in a migration.

## Writing an upgrade test

Call `useUpgradeTestDatabase('0001_schema_v1')` from `src/testing/database-upgrade.ts`
once at module scope, naming the journal tag the test starts from. It creates a fresh
disposable database from `template0` and runs the real Drizzle migrations through
that tag (inclusive), with their original SQL and journal metadata. It removes its
temporary migration folder and cleans up the database after the test file.
By default this pre-upgrade database has not run `applySecurity` (forced RLS and
column-level revokes); `migrateDatabase` applies it after the upgrade. Pass
`{ applySecurity: true }` to start from the secured state a real install of that
release had: the current `applySecurity` runs right after the starting migration,
so it must accept that schema. `database.appUrl` then connects as the app role, to
seed rows under row-level security the way the running app wrote them
(`database-upgrade.secured.test.ts`). A test file that imports the helper relatively
still imports it as `../testing/database-upgrade.js`, which places it in the test
project that starts a database.

Seed historical rows with plain SQL through `openConnection(database.maintenanceUrl)`;
current-schema factories can reference columns that did not exist then. Close the
seed connection in `finally`, call `migrateDatabase(database.maintenanceUrl)` to
apply all remaining migrations and current security checks, then assert the result
through `database.forGym`. Check every historical field and the migration's new
fields with `toMatchObject` so unrelated future columns need no fixture changes.
Only the starting tag belongs in the test: do not add down SQL, journal deletions,
or a count of later migrations. Appending a migration requires no helper changes.

## Startup and security

Before opening either the application or migration connection,
`assertSchemaCompatibility` checks the updater's `SCHEMA_ROLLBACK_FLOOR` against
`APP_VERSION`. `SCHEMA_RELEASE` and `SCHEMA_SNAPSHOT` identify recovery steps when
older code is refused. This metadata is supplied by the checked installation file
`schema-compatibility.yaml`; it adds no database table or migration. Keep that file
with the database. See [rollback](../../docs/updating.md#roll-back-a-release).

Database bootstrap creates `app` and `maintenance`. The app role has DML privileges,
no DDL, no TRUNCATE, and no membership in maintenance. Maintenance owns the database
and schema, has BYPASSRLS, and has no superuser, CREATEDB, or CREATEROLE privileges.

Call `migrateDatabase(maintenanceUrl)` before `initializeDatabase(appUrl)` and before
serving requests. Migration uses a dedicated connection and a session advisory lock.
After Drizzle finishes, `applySecurity` forces enabled RLS and restores the declared
write restrictions. `assertCatalog` then checks actual policies, role properties,
ownership, table and column privileges, tenant keys and foreign keys. Restore uses
the same migration/security entry point. A failed check prevents successful startup.

Advisory locks are registered in `src/locks.ts`. `advisoryLocks` holds the
(namespace, key) pairs for work shared by every gym (migrations, backups, job claims).
`gymAdvisoryLocks` holds the locks that take a gym ID, so one gym's work never waits
on another's: `lockGym(tx, name, gymId)` waits for the lock and holds it until the
transaction ends. Don't rename a registered name, since a release running beside an
older one would then take a different lock.

The security step never restores table-wide DML grants. It removes table and column
UPDATE permissions on immutable records, then grants only the five mutable outcome
columns on payment attempts and `reason` alone on class credit entries. Credit
entries cannot be deleted by app. Audit events allow INSERT and SELECT only. Waiver
signatures also allow DELETE, used only when a member's personal data is erased on
request; they are never updated. Gym deletion still cascades these rows through the
gym foreign key, because PostgreSQL runs cascades as the table owner (`maintenance`).

Only `gym_id` references cascade. Every reference between tenant tables is
`NO ACTION`: delete child rows explicitly, or archive (`active`, `retired_at`,
`revoked_at`) instead. Never use `ON DELETE SET NULL` on a composite reference:
PostgreSQL would also null `gym_id`, which fails and blocks gym deletion.

`system-tables.mjs` is the exhaustive inventory of system tables (tables a request
reaches before, or outside, a single gym), with each table's access kind and module
allowlist. The ESLint rule and the catalog check consume that same inventory.

System tables have forced RLS too, with policies for two contexts:

| Context | Set by | Sees |
| --- | --- | --- |
| Gym | `forGym` (`app.gym_id`) | Only its own gym's system rows: its `gyms` row (read and update, never insert or delete), domains, jobs, schedule cursors, sessions and webhook events. Never another gym's rows, install-level rows (no gym), identity or backup history. |
| System | `forSystem` (`app.system`, one transaction) or `systemDatabase()` (a separate pool with `app.system` on every connection, for the auth adapter, which runs its own queries) | Every system row, for tenancy lookup, authentication, job claiming, the webhook inbox, setup and restore. Grants no tenant data: gym-owned tables still require their gym. |

With neither context a connection sees no system rows and can't write any (fail
closed). Access kinds: `gym` (domains, jobs, schedule cursors, sessions, webhook events), `gym-config`
(`gyms`) and `system` (identity tables, backup history); the catalog check verifies
each table's exact policies, ENABLE and FORCE. A table the running image doesn't
declare has no inventory entry, so the check reads its kind from its policies, which
must match the gym policy or one access kind exactly (`docs/versioning.md`). This prevents accidental cross-gym
queries on the app role's ordinary connections; it doesn't constrain `maintenance`
(BYPASSRLS), and `forSystem` / `systemDatabase` are lint-limited to the
infrastructure modules the inventory lists (`systemDatabase` to `infra/auth`).
Tests in `system-access.test.ts` issue the forbidden queries directly to prove it.

Direct access is limited to the code that writes those rows: tenancy, settings,
setup, the gym CLI and demo for `gyms`; restore for re-encrypting `gyms` and
`auth_account` secrets; the webhook inbox and replay CLI for `stripe_events`.
Everyone else gets explicit fields or aggregates from a service (gym settings from
tenancy context or the settings service, job counts from `infra/jobs`, webhook
health from the inbox), never system-table rows.

The same rule rejects raw SQL outside reviewed infrastructure (tenancy, job
claiming, migrations, backup, restore), since raw SQL names tables without an
import the rule can check. Outside that infrastructure, app code may import only
query operators (`eq`, `and`, `inArray`, `desc`, `count`, ...) as values from
`drizzle-orm`; any other value import from any `drizzle-orm` path (`sql`, `SQL`,
`StringChunk`, `pgTable`, `drizzle`, default, namespace or dynamic imports) is
rejected, because each can name a table as text, as in ``.from(sql`gyms`)``.
Type-only imports are allowed. Tables come from `@plaingym/db`, where the
system-table check applies. Reaching `execute` or `$client` on a database handle
(dotted, bracketed or destructured) is rejected too. A reviewed exception elsewhere,
such as full-text search, needs an eslint-disable comment giving the reason. The
database client has no relational `tx.query` API for the same reason.

## Scoped access

`forGym(gymId, fn)` opens one short transaction, sets `app.gym_id` transaction-locally,
and supplies its Drizzle transaction to `fn`. Missing or reset context sees no tenant
rows. Malformed context errors. Nested scope calls are rejected. Every tenant
policy has both USING and WITH CHECK, and references between tenant tables include
`gym_id`. Use separate transactions for reserve, external I/O, and completion.

`forHousehold({ kind: 'user', gymId, householdId, userId }, fn)` verifies `household_users` inside
the gym transaction. Its callback gets named query functions, with no raw handle or
arbitrary predicates. Payers can read the household; non-payers can read their linked
member only. Invoice and payment-method queries require payer access; revoked cards
are never returned. `members()` and `member(id)` share one projection, which
excludes medical notes, check-in hashes and household PIN hashes and includes the
revision. Emergency contacts are included for logged-in household users only.
The caller supplies `userId` and `gymId` from authenticated request context.

The portal reads a household's history as pages and single lookups: `bookingPage`,
`booking`, `sessionBookings`, `attendancePage`, `attendanceCount`, `rankHistory`,
`membershipPage`, `signaturePage`, `signature`, `signedTemplates` and `invoicePage` filter,
order and project in SQL, inside the same grant, and a page answers `{ rows, total }`. An ID
outside the grant finds nothing. `members()` and `waiverTemplates()` stay whole: they are as
long as the household and the gym's current documents, not its history. The whole-history
reads (`bookings()`, `attendance()`, `ranks()`, `memberships()`, `invoices()`) have no
production caller and stay for the comparison tests; `waivers()` also serves signed-link
pages.

Signed-link pages call `forHousehold({ kind: 'signed_link', gymId, linkId, now }, fn)`.
The link ID must come from a verified token's request context; a submitted link ID
alone is not authorization. `now` comes from the injected request clock. Inside the
transaction the helper reloads the link, rejects revoked, used or expired rows,
and derives the household and resource from that row. Caller-supplied household
and resource claims cannot widen access.

| Link purpose | Available queries |
| --- | --- |
| `pay_invoice` | The linked invoice and its lines |
| `update_card` | Masked household payment methods |
| `sign_waiver` | The linked member, that member's signed waivers, and current gym templates |
| `onboarding` | Household members, their signed waivers, current gym templates, and masked payment methods |
| `unsubscribe` | Only `announcementPreference()` and `setAnnouncementOptOut(optedOut, now)` for the stored member |

The announcement preference exposes only the member's name and opt-out state.
Its mutation accepts no resource selectors, locks and rechecks the link and
member, and changes only that member's `announcement_opt_outs` row with an audit
in the same transaction. Pass the injected clock as a callback so expiry is
checked after acquiring the locks. Repeated opt-outs and resubscriptions are
no-ops. Other signed-link purposes and logged-in users cannot call these two
methods; an unsubscribe grant cannot call any of the other queries.

Every query checks the resolved grant. A disallowed query throws `HouseholdAccessError`, whose
`code` is `household_access_denied` or `payer_access_required`; map the code, never the message.
An ID outside an allowed resource scope returns no rows. Signed links cannot read household profile,
booking, attendance, rank or membership data, or emergency contacts.
`waiverTemplates()` is read-only: it takes the highest version of each template
name, then drops families whose latest version is retired, so retiring a template
never brings back an older version. Logged-in payers and
adult members can also read those current templates.

Example:

```ts
await forHousehold({ kind: 'user', gymId, householdId, userId }, async (queries) => {
  const members = await queries.members();
  const bookings = await queries.bookingPage({ memberId: members[0].id }, { limit: 50, offset: 0 });
  return { members, bookings };
});
```

Services supply event time from their injected clock to `writeAudit(tx, event)`.
They must redact secrets and sensitive fields from before/after data.
Schema timestamp defaults record insertion time; UUIDv7 generation uses the process
clock and cryptographic randomness. UUIDs are not a total ordering within a millisecond.

Amounts are integers in the currency's minor units (cents for USD, whole yen for
JPY; `@plaingym/shared/money`), with a currency. Each gym has one billing currency:
plans, charge types, memberships and invoices reference `(gym_id, currency)` on
`gyms`, and invoice lines, attempts and payments reference their invoice's
currency (refunds, their payment's). Once anything references it, the gym's
currency cannot change, so existing amounts are never relabelled. Tax rates are
integer millionths (99,750 = 9.975%); family discounts are basis points. A plan or
charge type can carry several tax rates (for example GST and QST), each stated as
its own line and computed on the pre-tax amount, never compounded. Tax lines
snapshot their rate and inclusive flag at issue, and their description holds the
tax name, so editing a rate never rewrites issued receipts. Compute tax in integer
arithmetic with one documented rounding rule. All instant columns are timestamptz.
Billing-calendar dates, commitment end dates and birth dates use date. Template wall-clock times are validated HH:MM text.
Auth rate-limit time is epoch milliseconds to match the authentication adapter.

A cycle invoice is unique per gym, household, kind and due date. One-off invoices
can share a due date. Issued invoices carry a per-gym display number from
`allocateInvoiceNumber(tx, gymId)`, called in the issuing transaction: it locks the
gym's sequence row, so numbers are never reused (a rolled-back issue rolls back its
number too). Drafts have no number; delete abandoned drafts rather than voiding
them. Look invoices up and authorize them by UUID, never by number. Only one pending attempt exists per invoice. Attempt number,
amount, currency, customer and saved payment method cannot be updated by app.
An active booking is unique per member/session; capacity still requires the service
to lock the session row for every booking or capacity change. Waitlist positions
keep gaps: allocate the maximum plus one under that lock, promote the lowest, and
never renumber; show queue rank separately.

A household has at most one default card (`payment_methods.is_default`), which can't
be revoked; since the flag is on the household's own row, the default always
belongs to the household. A member has at most one portal login; a household may
have several payers. A staff profile needs no login. A promotion records its rank
system, and both its rank and its program must belong to that system. Audit actors
are a user, a kiosk device (in the same gym) or the system, each with exactly its
own reference.

Staff-editable rows carry a `revision`. Update contracts send the revision the
client read; the update uses `revisionGuard` to match it and increment it in one
statement, and `assertRevised` turns a stale save into `RevisionConflictError`.

Waiver snapshots are text, preserving their UTF-8 bytes exactly. Snapshot hashes
and image digests are lowercase SHA-256 hex. The signing service computes them
from the actual bytes; the database checks their format and denies later changes.
Storage references contain keys, never image bytes.

Signed links reference invoices and members through composite foreign keys containing
gym and household IDs. A CHECK requires only `invoice_id` for `pay_invoice`, only
`member_id` for `sign_waiver` and `unsubscribe`, and neither for `update_card` or `onboarding`.
Audit target IDs are polymorphic identifiers without foreign keys. Household Stripe
customer IDs and payment-method processor IDs are processor references, not local
row IDs.

## Encrypted fields

`src/encrypted-fields.ts` lists the integration configuration envelopes (including the gym's Google OAuth client), gym QR key,
backup blob-naming key, and OAuth tokens. The auth adapter must encrypt/decrypt its
registered token fields. Password, PIN, check-in and capability hashes are hashes,
not reversible encryption. The age public key and backup destination metadata are
not secrets. Do not place credentials inside general settings or destination JSON.
Restore enumerates this registry; unknown secret classes throw.

## Database tests

With Docker running, `pnpm test` starts disposable PostgreSQL automatically.
To use an existing server, set `TEST_DATABASE_URL` with
`TEST_MAINTENANCE_DATABASE_URL` and `TEST_DATABASE_ADMIN_URL` (or the matching
`TEST_MAINTENANCE_PASSWORD` and `TEST_POSTGRES_PASSWORD`). All three must address
the same server. The admin connection is used only to create and drop randomly
named test databases, never for test application queries. Tests never read `.env`,
and never migrate or erase the database named in `TEST_DATABASE_URL`.

Global setup builds and verifies a migrated template, then closes its connections.
Each integration file calls `useTestDatabase()` to get a fresh clone and an app pool
of two connections. Clones and the template are removed at teardown. Factories
accept a table name, gym UUID and typed overrides. Create the gym first; required
foreign-key dependencies are inserted automatically within that gym:

```ts
const database = useTestDatabase();
const factory = createFactories(database);
const gymId = uuidv7();
await factory('gyms', gymId);
```
