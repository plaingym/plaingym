# Database schema

Schema v1 contains 51 PostgreSQL tables. `src/schema/` is the source of truth;
`src/migrations/0001_schema_v1.sql` is generated by Drizzle. Its journal entry has
`idx: 1` and its snapshot is `meta/0001_snapshot.json`, so the next generated
migration is numbered 0002. Keep the SQL file name, journal tag, index and snapshot
name aligned.

Run generation from this package with `pnpm exec drizzle-kit generate --name <name>`.
Commit the generated SQL and metadata together. Add an SPDX SQL comment to generated
SQL files. Never edit a table definition directly in a migration.

## Startup and security

Database bootstrap creates `app` and `maintenance`. The app role has DML privileges,
no DDL, no TRUNCATE, and no membership in maintenance. Maintenance owns the database
and schema, has BYPASSRLS, and has no superuser, CREATEDB, or CREATEROLE privileges.

Call `migrateDatabase(maintenanceUrl)` before `initializeDatabase(appUrl)` and before
serving requests. Migration uses a dedicated connection and a session advisory lock.
After Drizzle finishes, `applySecurity` forces enabled RLS and restores the declared
write restrictions. `assertCatalog` then checks actual policies, role properties,
ownership, table and column privileges, tenant keys and foreign keys. Restore uses
the same migration/security entry point. A failed check prevents successful startup.

The security step never restores table-wide DML grants. It removes table and column
UPDATE permissions on immutable records, then grants only the five mutable outcome
columns on payment attempts. Audit events and waiver signatures allow INSERT and
SELECT only. Gym deletion still cascades their rows through the gym foreign key,
because PostgreSQL runs cascades as the table owner (`maintenance`); ordinary row
mutation by `app` remains prohibited.

Only `gym_id` references cascade. Every reference between tenant tables is
`NO ACTION`: delete child rows explicitly, or archive (`active`, `retired_at`,
`revoked_at`) instead. Never use `ON DELETE SET NULL` on a composite reference:
PostgreSQL would also null `gym_id`, which fails and blocks gym deletion.

`system-tables.mjs` is the exhaustive exemption inventory and module allowlist.
The ESLint rule consumes that same inventory. System rows are visible to the app
role without RLS, so their named infrastructure modules must enforce the request
boundary. The migration catalog check rejects undeclared exemptions.

Direct access is limited to the code that writes those rows: tenancy, settings,
setup, the gym CLI and demo for `gyms`; restore for re-encrypting `gyms` and
`auth_account` secrets; the webhook inbox and replay CLI for `stripe_events`.
Everyone else gets explicit fields or aggregates from a service (gym settings from
tenancy context or the settings service, job counts from `infra/jobs`, webhook
health from the inbox), never system-table rows.

The same rule rejects raw SQL outside reviewed infrastructure (tenancy, job
claiming, migrations, backup, restore), since raw SQL names tables without an
import the rule can check. Outside that infrastructure, app code may import only
query operators (`eq`, `and`, `inArray`, `desc`, `count`, ...) as values from
`drizzle-orm`; any other value import from any `drizzle-orm` path (`sql`, `SQL`,
`StringChunk`, `pgTable`, `drizzle`, default, namespace or dynamic imports) is
rejected, because each can name a table as text, as in ``.from(sql`gyms`)``.
Type-only imports are allowed. Tables come from `@plaingym/db`, where the
system-table check applies. Reaching `execute` or `$client` on a database handle
(dotted, bracketed or destructured) is rejected too. A reviewed exception elsewhere,
such as full-text search, needs an eslint-disable comment giving the reason. The
database client has no relational `tx.query` API for the same reason.

## Scoped access

`forGym(gymId, fn)` opens one short transaction, sets `app.gym_id` transaction-locally,
and supplies its Drizzle transaction to `fn`. Missing or reset context sees no tenant
rows. Malformed context errors. Nested scope calls are rejected. Every tenant
policy has both USING and WITH CHECK, and references between tenant tables include
`gym_id`. Use separate transactions for reserve, external I/O, and completion.

`forHousehold({ kind: 'user', gymId, householdId, userId }, fn)` verifies `household_users` inside
the gym transaction. Its callback gets named query functions, with no raw handle or
arbitrary predicates. Payers can read the household; non-payers can read their linked
member only. Invoice and payment-method queries require payer access; revoked cards
are never returned. `members()` and `member(id)` share one projection, which
excludes medical notes, check-in hashes and household PIN hashes and includes the
revision. Emergency contacts are included for logged-in household users only.
The caller supplies `userId` and `gymId` from authenticated request context.

Signed-link pages call `forHousehold({ kind: 'signed_link', gymId, linkId, now }, fn)`.
The link ID must come from a verified token's request context; a submitted link ID
alone is not authorization. `now` comes from the injected request clock. Inside the
transaction the helper reloads the link, rejects revoked, used or expired rows,
and derives the household and resource from that row. Caller-supplied household
and resource claims cannot widen access.

| Link purpose | Available queries |
| --- | --- |
| `pay_invoice` | The linked invoice and its lines |
| `update_card` | Masked household payment methods |
| `sign_waiver` | The linked member, that member's signed waivers, and current gym templates |
| `onboarding` | Household members, their signed waivers, current gym templates, and masked payment methods |

Every query checks the resolved grant. A disallowed query throws; an ID outside an
allowed resource scope returns no rows. Signed links cannot read household profile,
booking, attendance, rank or membership data, or emergency contacts.
`waiverTemplates()` is read-only: it takes the highest version of each template
name, then drops families whose latest version is retired, so retiring a template
never brings back an older version. Logged-in payers and
adult members can also read those current templates.

Example:

```ts
await forHousehold({ kind: 'user', gymId, householdId, userId }, async (queries) => {
  const members = await queries.members();
  const bookings = await queries.bookings();
  return { members, bookings };
});
```

Services supply event time from their injected clock to `writeAudit(tx, event)`.
They must redact secrets and sensitive fields from before/after data.
Schema timestamp defaults record insertion time; UUIDv7 generation uses the process
clock and cryptographic randomness. UUIDs are not a total ordering within a millisecond.

Amounts are integer cents with a currency. Each gym has one billing currency:
plans, charge types, memberships and invoices reference `(gym_id, currency)` on
`gyms`, and invoice lines, attempts and payments reference their invoice's
currency (refunds, their payment's). Once anything references it, the gym's
currency cannot change, so existing amounts are never relabelled. Tax rates are
integer millionths (99,750 = 9.975%); family discounts are basis points. A plan or
charge type can carry several tax rates (for example GST and QST), each stated as
its own line and computed on the pre-tax amount, never compounded. Tax lines
snapshot their rate and inclusive flag at issue, and their description holds the
tax name, so editing a rate never rewrites issued receipts. Compute tax in integer
arithmetic with one documented rounding rule. All instant columns are timestamptz.
Billing-calendar dates, commitment end dates and birth dates use date. Template wall-clock times are validated HH:MM text.
Auth rate-limit time is epoch milliseconds to match the authentication adapter.

A cycle invoice is unique per gym, household, kind and due date. One-off invoices
can share a due date. Issued invoices carry a per-gym display number from
`allocateInvoiceNumber(tx, gymId)`, called in the issuing transaction: it locks the
gym's sequence row, so numbers are never reused (a rolled-back issue rolls back its
number too). Drafts have no number; delete abandoned drafts rather than voiding
them. Look invoices up and authorize them by UUID, never by number. Only one pending attempt exists per invoice. Attempt number,
amount, currency, customer and saved payment method cannot be updated by app.
An active booking is unique per member/session; capacity still requires the service
to lock the session row for every booking or capacity change. Waitlist positions
keep gaps: allocate the maximum plus one under that lock, promote the lowest, and
never renumber; show queue rank separately.

A household has at most one default card (`payment_methods.is_default`), which can't
be revoked; since the flag is on the household's own row, the default always
belongs to the household. A member has at most one portal login; a household may
have several payers. A staff profile needs no login. A promotion records its rank
system, and both its rank and its program must belong to that system. Audit actors
are a user, a kiosk device (in the same gym) or the system, each with exactly its
own reference.

Staff-editable rows carry a `revision`. Update contracts send the revision the
client read; the update uses `revisionGuard` to match it and increment it in one
statement, and `assertRevised` turns a stale save into `RevisionConflictError`.

Waiver snapshots are text, preserving their UTF-8 bytes exactly. Snapshot hashes
and image digests are lowercase SHA-256 hex. The signing service computes them
from the actual bytes; the database checks their format and denies later changes.
Storage references contain keys, never image bytes.

Signed links reference invoices and members through composite foreign keys containing
gym and household IDs. A CHECK requires only `invoice_id` for `pay_invoice`, only
`member_id` for `sign_waiver`, and neither for `update_card` or `onboarding`.
Audit target IDs are polymorphic identifiers without foreign keys. Household Stripe
customer IDs and payment-method processor IDs are processor references, not local
row IDs.

## Encrypted fields

`src/encrypted-fields.ts` lists the integration configuration envelopes, gym QR key,
backup blob-naming key, and OAuth tokens. The auth adapter must encrypt/decrypt its
registered token fields. Password, PIN, check-in and capability hashes are hashes,
not reversible encryption. The age public key and backup destination metadata are
not secrets. Do not place credentials inside general settings or destination JSON.
Restore enumerates this registry; unknown secret classes throw.

## Database tests

With Docker running, `pnpm test` starts disposable PostgreSQL automatically.
When `DATABASE_URL` is set, also provide `MAINTENANCE_DATABASE_URL` and
`TEST_DATABASE_ADMIN_URL`, or the matching `MAINTENANCE_PASSWORD` and
`POSTGRES_PASSWORD`. All three must address the same server. The admin connection
is used only to create and drop randomly named test databases, never for test
application queries. Tests do not migrate or erase the database named in DATABASE_URL.

Global setup builds and verifies a migrated template, then closes its connections.
Each integration file calls `useTestDatabase()` to get a fresh clone and an app pool
of two connections. Clones and the template are removed at teardown. Factories
accept a table name, gym UUID and typed overrides. Create the gym first; required
foreign-key dependencies are inserted automatically within that gym:

```ts
const database = useTestDatabase();
const factory = createFactories(database);
const gymId = uuidv7();
await factory('gyms', gymId);
const member = await factory('members', gymId);
```

`expectCrossGymDenied` and `expectCrossHouseholdDenied` accept request closures for
route-level isolation tests. Catalog tests deliberately break policies and grants
to prove the checker fails. Pool tests exercise both commits and rollbacks.
